# v4.2.0 Roadmap: Cognitive Intelligence

> **核心目标**：让 Tool-Driven 架构从「可用」走向「智能」——不增加新 tools，而是让现有 tools 更聪明、更可观测、更可回溯。
> **状态**：planning
> **创建时间**：2026-05-11
> **预计完成**：2026-06-01
> **维护者**：PM（程序员 / 开发经理）

---

## 1. 问题诊断（v4.1.0 遗留与深化）

> **PM 诊断来源**：实际运行环境审查、测试报告、文件系统状态分析

### 问题 1：Agent 调用 tools 的「黑箱」
**风险等级**：中等
**具体表现**：
- Agent 调用 `get_planning_guide` → `create_plan` → `update_task_status` 的序列，只有最终文件结果，没有中间决策记录
- 当任务出现偏差时，无法回溯「Agent 当时为什么做了这个决定」
- `self_diagnose` 只能返回当前快照，无法展示「Agent 是怎么走到这里的」
**根因**：v4.1.0 设计了 tools，但没有设计「认知轨迹」记录机制。
**影响**：调试困难、事后复盘缺失、Agent 无法从自己的历史决策中学习。

### 问题 2：templates/ 是静态文本，无法动态适配
**风险等级**：低（体验债务）
**具体表现**：
- `get_planning_guide("draft")` 返回的 `planning.md` 模板是固定的，无法根据当前 task 的 `phases` 配置动态生成步骤
- 模板中包含大量「占位符」，Agent 需要自行判断哪些段落适用
- 不同项目的任务类型（编码任务 vs 调研任务）使用同一套模板
**根因**：v4.1.0 将 SKILL.md 重构为 templates/ 静态 Markdown，但未引入条件渲染。
**影响**：模板泛化、Agent 理解成本增加、指导精度下降。

### 问题 3：历史任务无法被「复用」
**风险等级**：中等
**具体表现**：
- 完成并归档的任务（`archive/` 目录）只是文件搬迁，没有建立索引
- 当 Agent 面对新任务时，无法检索「之前是否做过类似的」
- `create_plan()` 每次都从零开始，没有案例参考
**根因**：v4.1.0 实现了 `archive_task` 工具，但未建立归档索引和相似度检索。
**影响**：重复劳动、知识无法累积、Agent 长期成长受限。

### 问题 4：诊断信息单薄，缺乏预警
**风险等级**：中等
**具体表现**：
- `self_diagnose` 返回 `{ taskStatus, phase, deviations, toolsAvailable }`，但没有「趋势分析」
- 无法预警「当前 phase 已超时」、「偏差频率异常增高」等问题
- Agent 只能在问题发生后调用 diagnose，不能提前感知
**根因**：v4.1.0 的 diagnose 是快照式，非趋势式。
**影响**：Agent 被动响应、缺乏前瞻性调节。

### 技术债务 5：git tag 与版本号管理混乱
**风险等级**：低（工程规范）
**具体表现**：
- package.json version = `4.1.0`，但最新 git tag 为 `v2.0.0`
- v3.x 和 v4.x 均未打 tag
- TODO.md 文件头仍写 `v4.0.0 → v4.1.0`
**根因**：版本发布流程未规范化。
**影响**：版本追踪困难、回滚风险。

## 2. 设计哲学：从「工具暴露」到「认知增强」

v4.1.0 解决了「插件越界」问题——从「代劳」变成「赋能」。
v4.2.0 进一步解决「赋能之后 Agent 如何更聪明」的问题。

**核心原则**：
- **不增加新 tools**：13 个 tools 已经够用，增加 tools 会增加 Agent 的认知负担
- **增强现有 tools 的返回内容**：让 `get_task_status`、`self_diagnose`、`get_planning_guide` 返回更智能的信息
- **透明化认知过程**：记录 Agent 的 tool 调用序列，让「思考过程」可追溯
- **累积历史智慧**：归档任务建立索引，新任务可以站在旧任务的肩膀上

## 3. 解决方案

### 方案 1：认知轨迹（Cognitive Trace）

**设计**：
在 `.agent/cognitive-traces/{runId}.jsonl` 中记录 Agent 的每次 tool 调用：

```jsonl
{"t":1715408123,"tool":"get_task_status","input":{"runId":"xxx"},"output":{"status":"draft"},"reason":"了解当前状态"}
{"t":1715408125,"tool":"get_planning_guide","input":{"phase":"draft"},"output":{"guide":"..."},"reason":"制定计划"}
{"t":1715408130,"tool":"create_plan","input":{"goal":"..."},"output":{"task":"..."},"reason":"创建任务"}
```

**实现**：
- 在 `src/tools/index.js` 的 `registerTools()` 中，为每个 tool handler 包装一层「轨迹记录器」
- 不侵入 tool 业务逻辑，仅在外层 wrap
- 轨迹文件按 `runId` 隔离，自动归档到 `archive/` 时一并迁移

**对现有工具的影响**：
- `self_diagnose`：新增返回字段 `cognitiveTraceSummary` —— 最近 5 次 tool 调用摘要
- `get_task_status`：新增返回字段 `toolCallCount`、`lastToolCall`、`elapsedSinceLastCall`

**验收标准**：
- 每次 tool 调用在 100ms 内完成轨迹写入（异步，不阻塞）
- 轨迹文件格式为 JSONL，可用 `jq` 查询
- 归档时轨迹文件随 task 一起迁移
- `self_diagnose` 返回的 `cognitiveTraceSummary` 可读性良好

---

### 方案 2：模板智能渲染（Smart Templates）

**设计**：
templates/ 中的 Markdown 文件引入轻量级条件语法：

```markdown
## 计划阶段

{{#if phase === "draft"}}
请根据以下约束制定 Plan：
- 目标：{{task.goal}}
- 约束：{{task.constraints}}
- 成功标准：{{task.successCriteria}}
{{/if}}

{{#if phase === "revising"}}
当前计划需要修订。以下是历史偏差摘要：
{{#each deviations}}
- {{type}}: {{description}}
{{/each}}
{{/if}}
```

**实现**：
- 引入轻量级模板引擎（如 `handlebars` 或自研 50 行正则替换器）
- `get_planning_guide`、`get_monitoring_guide`、`get_regulation_guide`、`get_development_guide` 在返回前，将模板与当前 task 状态合并
- 保持向后兼容：纯文本模板无需改动即可工作

**对现有工具的影响**：
- 4 个 `get_*_guide` tools 的返回值从「静态文本」变为「动态渲染文本」
- 返回值质量提升，Agent 获得更精准的指导

**验收标准**：
- 模板渲染时间 < 50ms
- 纯文本模板零改动即可兼容
- 条件语法简单到 Agent 无需学习（仅插件内部使用）
- 新增 3 个「任务类型专用模板」：编码任务、调研任务、文档任务

### 方案 3：任务相似度与案例推荐（Case-Based Planning）

**设计**：
在 `.agent/state/case-index.sqlite` 中维护归档任务的索引：

| 字段 | 说明 |
|------|------|
| runId | 任务ID |
| goal | 任务目标（文本） |
| goalEmbedding | 目标语义向量（简化版：关键词集合） |
| phases | 阶段数 |
| totalDeviations | 总偏差数 |
| outcome | 结果（success / partial / failure） |
| archivedAt | 归档时间 |

**实现**：
- 在 `archive_task()` 时，提取 task 的关键特征写入索引
- 在 `create_plan()` 时，检索索引中 `goal` 相似度最高的 3 个历史任务
- 相似度算法：先基于关键词 Jaccard 相似度（轻量、无外部依赖），后续可升级为向量相似度
- `create_plan()` 返回值新增字段：`similarCases: [{ runId, goal, outcome, relevance }]`

**对现有工具的影响**：
- `create_plan()`：新增返回相似案例
- `archive_task()`：新增索引写入

**验收标准**：
- 索引查询时间 < 200ms（基于 SQLite LIKE + 关键词匹配）
- 推荐的相似案例相关度 > 0.5（人工验证 10 组）
- 索引自动清理：超过 `config.archive.maxArchivedTasks` 时删除最旧的索引记录

### 方案 4：诊断增强 v2（Diagnosis v2）

**设计**：
`self_diagnose` 从「快照式」升级为「趋势式」：

```json
{
  "taskStatus": "active",
  "phase": 2,
  "deviations": [...],
  "toolsAvailable": [...],
  "cognitiveTraceSummary": [...],
  "trendAnalysis": {
    "phaseElapsedTime": "45min",        // 当前 phase 已耗时
    "avgPhaseTime": "30min",            // 历史同类型任务平均 phase 耗时
    "deviationRate": "2/hour",          // 偏差频率
    "riskFlags": [                      // 风险预警
      "phase_time_over_avg: 当前阶段耗时超过历史均值 50%",
      "high_deviation_rate: 偏差频率高于正常水平"
    ]
  }
}
```

**实现**：
- 利用认知轨迹数据计算 phase 耗时、偏差频率
- 利用案例索引计算「历史同类型任务均值」
- 风险阈值可配置：`config.diagnosis.riskThresholds`

**对现有工具的影响**：
- `self_diagnose()`：返回值大幅增强
- 新增配置项：`diagnosis.riskThresholds.phaseTimeMultiplier`（默认 1.5）

**验收标准**：
- 风险预警准确率 > 80%（人工验证 20 组）
- 不增加外部依赖（纯本地 SQLite 计算）
- 诊断信息不过载——最多返回 3 条 riskFlags

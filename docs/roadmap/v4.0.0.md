# v4.0.0 Roadmap: Project Context Layer & Multi-Agent Collaboration

> **核心目标**：建立「项目上下文层」，使多 Agent 能在同一项目中协作。
> **状态**：active
> **创建时间**：2026-05-08
> **预计完成**：2026-05-15

---

## 1. 问题诊断

### 问题1：项目没有标准化的协作基础设施
**现状**：不同 Agent 接手同一项目时，无法快速理解项目结构和当前状态。
**根因**：没有定义标准的项目级文件系统协作协议，Agent 不知道文件该放哪、怎么找其他 Agent 的成果、如何声明自己的编辑意图。
**影响**：每次新项目接入都需要重新探索，协作效率低。

### 问题2：缺少系统化的协作方法论
**现状**：Agent 各自为政，用户需要在多个 Agent 之间手动协调。
**根因**：没有定义 Agent 如何「举手」请求协助、如何向用户汇报进度、插件应该在什么时机督促 Agent。
**影响**：Agent 执行任务时沉默执行，用户不知道进度；Agent 遇到困难时死等用户发现。

### 问题3：插件 Hook 注入机制与职责不匹配
**现状**：
- regulation skill 被实例化但从未注入，Agent 无法获得归因分析所需的上下文数据
- monitoring 在 `before_prompt_build` 注入，但此时本轮输出尚未生成，无法做「输出 vs 预期」对比
- working-memory 标记为 `reference_only`，Agent 在 active 阶段看不到 Session 管理规则
**根因**：Hook 的 `injected_at` 与 Agent 在该时机能完成的工作不匹配。
**影响**：Agent 被 skill 告知要做某事，但插件从未提供执行所需的数据或时机。

## 2. 目标凝练

| 目标 | 对应问题 | 成功标准 |
|------|---------|----------|
| **建立项目上下文层（Project Context Layer）** | 问题1 | 任意项目接入后，Agent 可通过标准化文件系统协作 |
| **设计人机协同协作系统** | 问题2 | 用户分配→Agent执行→举手请求→插件督促→用户确认，形成闭环 |
| **修复插件 Hook 职责对齐** | 问题3 | 每个 skill 在正确的时机注入，Agent 获得所需数据 |

## 3. 解决方法：系统方法论设计

### 3.1 系统定义：项目上下文层

**定义**：「项目上下文层」是位于 OpenClaw 会话层之下的持久化协作层。它通过标准化的项目目录结构和文件协议，使多个独立的 Agent Session 能够在同一项目中共享上下文、协作完成任务。

**核心特性**：
- **持久化**：数据存储在项目文件中，不依赖 Session 内存
- **标准化**：所有项目遵循相同的目录结构和文件格式
- **可发现**：Agent 进入项目后，通过读取标准文件即可理解项目状态
- **无共享内存**：Agent 之间不通过 `sessions_send` 通信，只通过文件系统读写协作

### 3.2 系统元件（Components）

项目上下文层由以下核心元件组成：

#### 元件1：四文件契约（The Four-File Covenant）
每个项目必须具备的四个核心文件，作为 Agent 的「上下文基线」：

| 元件 | 职责 | 内容 | 维护者 |
|------|------|------|--------|
| **README.md** | 项目总览 | 项目定位、目录结构说明、关键文件索引、快速开始指南 | Agent / 用户 |
| **metadata.json** | 机器可读架构 | 模块列表、技能列表、Agent 能力定义、协作模式配置 | Agent |
| **SKILL.md**（项目级） | 操作手册 | 项目特有的工作流程、工具使用规范、输出格式要求 | Agent |
| **TODO.md** | 进度看板 | 当前任务状态、进行中任务、待确认任务、已完成任务 | Agent / 用户 |

**设计原则**：
- README 是「人类视角」的总览，metadata.json 是「机器视角」的结构，两者互补
- SKILL.md 是「过程规范」，TODO.md 是「状态跟踪」，两者共同支撑协作执行
- 四文件必须位于项目根目录，Agent 进入项目时优先读取

#### 元件2：.openclaw/ 元数据层
位于项目根目录下的隐藏目录，存储协作过程中产生的元数据：

| 子目录 | 职责 | 结构 | 读写规则 |
|--------|------|------|----------|
| **events/** | 事件流 | 按天分文件夹：`events/{YYYY-MM-DD}/` | Agent 只写入 |
| **locks/** | 并发控制 | 单文件：`locks/{文件路径替换-为-}.json` | Agent 创建/删除 |
| **decisions/** | 决策存档 | 单文件：`decisions/{YYYYMMDD-HHMM}-标题.md` | Agent 写入 |
| **tasks/** | 任务历史 | 单文件：`tasks/{YYYYMMDD}-{task-id}.md` | 只读参考 |

**events/ 详细设计**：
- **目录结构**：`.openclaw/events/{YYYY-MM-DD}/`
- **文件命名**：`{HH-MM-SS}.md`（精确到秒，单文件记录完整事件）
- **文件内容**：需求 → 计划 → 偏差 → 归因（单文件闭环）
  ```markdown
  # 事件 {HH-MM-SS}
  
  > **时间**：{YYYY-MM-DD HH:MM:SS}
  > **触发者**：{user | agent-id | plugin}
  
  ---
  
  ## 1. 需求（Requirement）
  {用户原始需求或 Agent 接收到的任务}
  
  ## 2. 计划（Plan）
  {制定的执行计划：步骤、验收标准、预估时间}
  
  ## 3. 执行（Execution）
  {实际执行过程、完成的工作、产出的文件}
  
  ## 4. 偏差（Deviation）
  {执行中发现的偏差}
  - 偏差类型：{output_mismatch | doc_lag | session_misuse | other}
  - 描述：{具体描述}
  
  ## 5. 归因（Attribution）
  {偏差产生的原因分析}
  - 根本原因：{分析结果}
  - 影响评估：{影响范围}
  - 策略更新：{后续调整建议}
  
  ## 6. 结果（Outcome）
  {事件最终状态：完成 / 修正 / 放弃}
  ```
- **设计原则**：一个事件一个文件，从需求到归因完整记录，不拆分到多个文件
- **Agent 行为**：只写入新文件，不修改已有文件
- **示例**：`.openclaw/events/2026-05-08/18-30-00.md` — 单次完整事件

#### 元件3：业务目录层
项目实际的业务内容存储目录：

| 目录 | 职责 | 访问规则 |
|------|------|----------|
| **uploads/** | 用户上传的原始材料 | Agent 只读，不可写入 |
| **manuscripts/** | Agent 工作草稿（进行中、未确认） | Agent 读写 |
| **docs/** | 定稿（用户已确认的成果） | Agent 只读（写入需用户确认） |
| **knowledge/** | 项目积累的知识（笔记和综述） | Agent 读写 |
| **temp/** | 临时文件和归档草稿 | Agent 读写 |

**设计原则**：
- uploads/ 是「输入层」，用户提供的原始材料
- manuscripts/ 是「工作层」，Agent 的草稿和中间产出
- docs/ 是「输出层」，经用户确认的最终成果
- 文件从 manuscripts/ 到 docs/ 必须经过用户确认（[APPROVED]）

#### 元件4：插件督促层
由 `agent-self-development` 插件提供的 Hook 注入机制：

| 时机 | 注入元件 | 职责 |
|------|----------|------|
| `before_prompt_build`（任务启动） | planning skill + 项目上下文 | 督促 Agent 制定计划、读取项目上下文 |
| `before_prompt_build`（执行中） | monitoring skill | 督促 Agent 汇报进度 |
| `after_tool_call`（文件变更后） | project-context skill | 检测产出，提醒 Agent 更新文档或举手请求协助 |
| `before_agent_finalize`（完成前） | monitoring skill | 督促 Agent 自检、请求用户确认 |

**设计原则**：
- 插件不替 Agent 决策，只「提醒」和「注入上下文」
- 注入的内容必须是 Agent 在该时机能执行的操作（如制定计划、汇报进度）
- 避免注入需要「未来数据」的内容（如本轮尚未生成的输出）

#### 元件5：.openclawignore 可见性控制
定义 Agent 对项目文件的可见性边界：

| 规则类型 | 示例 | Agent 行为 |
|----------|------|-----------|
| 完全隐藏 | `.env`, `.git/`, `node_modules/` | 对 Agent 不存在，提问时回答"无此文件" |
| 只读 | `uploads/` | 可读但不可写，写入操作被拒绝 |
| 透明 | `.openclaw/locks/` | 锁文件对 Agent 透明，冲突检测由插件处理 |

### 3.3 系统交互（Interaction Protocol）

系统由三类参与者组成，它们通过文件系统和 Hook 注入交互：

```
参与者：
  ├─ 用户（Human）
  ├─ Agent（执行者，如 main / writer / coder）
  └─ 插件（Plugin，如 agent-self-development）

交互媒介：
  ├─ 文件系统（持久化协作层）
  └─ Hook 注入（实时提醒层）
```

#### 交互1：用户 → Agent（任务分配）

**协议**：用户通过对话直接分配任务给特定 Agent
**信息流向**：用户描述需求 → Agent 读取项目上下文 → Agent 理解任务
**文件系统影响**：Agent 在 TODO.md 标记任务为「进行中」
**约束**：用户根据 Agent 特性分配任务（如 "main，你擅长系统配置，初始化项目"）

#### 交互2：Agent → 文件系统（工作产出）

**协议**：Agent 将产出写入 manuscripts/，完成自检后请求用户确认
**信息流向**：Agent 工作 → 写入 manuscripts/ → 在 TODO.md 标记「待确认」
**文件系统影响**：
- manuscripts/ 新增文件
- TODO.md 任务状态变更
- .openclaw/events/ 追加工作记录
**约束**：Agent 不可直接写入 docs/，必须经过用户确认

#### 交互3：Agent → 用户（举手请求）

**协议**：Agent 发现需要其他 Agent 能力时，写入 TODO.md 并汇报用户
**信息流向**：
1. Agent A 继续执行自己擅长的部分（不阻塞）
2. Agent A 在 TODO.md「待分配（用户协调）」写入子任务
3. Agent A 向用户汇报：「我擅长 X，但发现需要 Y。建议分配给擅长 Y 的 Agent B。我继续处理 X。」
4. 用户收到后，将子任务分配给 Agent B
**文件系统影响**：TODO.md 新增「待分配」任务项

#### 交互4：插件 → Agent（督促提醒）

**协议**：插件通过 Hook 在关键时机注入提醒内容
**信息流向**：
- 任务启动时：注入「请制定执行计划」
- 执行中时：注入「请汇报当前进度」
- 文件变更后：注入「请确认是否需要协助」
- 完成前：注入「请自检并请求用户确认」
- 偏差检测时：注入「请输出 [STATUS: revising]」
- 归因分析时：注入「请按 regulation skill 分析偏差原因」
**约束**：插件只提醒，不替 Agent 决策；Agent 可忽略提醒（但需承担后果）
- Agent 响应后，将完整上下文（计划/偏差/归因）写入 `.openclaw/events/{YYYY-MM-DD}/{HH-MM}-{事件简述}.md`

#### 交互5：Agent ↔ Agent（文件系统协作）

**协议**：多个 Agent 通过读写共享文件协作，不通过 `sessions_send`
**信息流向**：
- Agent A 将中间成果写入 manuscripts/ 或 knowledge/notes/
- Agent B 读取同一文件，继续工作
- 若编辑同一文件，通过 .openclaw/locks/ 检测冲突
**约束**：
- 禁止 Agent 之间直接对话（`sessions_send`）
- 所有协作必须通过文件系统
- 冲突时由用户裁定或 Agent 协商

#### 交互6：用户 → 文件系统（最终确认）

**协议**：用户通过标记确认 Agent 成果
**信息流向**：用户检查 manuscripts/ → 输出 [APPROVED] 或 [REJECTED]
**文件系统影响**：
- [APPROVED]：文件从 manuscripts/ 移到 docs/，任务移到「已完成」
- [REJECTED]：任务回到「进行中」，Agent 修正

### 3.4 系统组织（Architecture）

项目上下文层采用**三层架构**组织：

```
┌─────────────────────────────────────────────────────────────┐
│ 第 3 层：实时意图层（Ephemeral）                              │
│ 生命周期：单轮对话                                              │
│ 内容：用户输入、Agent 输出、插件注入的提醒                       │
│ 存储位置：Session 内存（不持久化）                              │
└─────────────────────────────────────────────────────────────┘
                              ↑↓ 每轮对话读写
┌─────────────────────────────────────────────────────────────┐
│ 第 2 层：动态协作层（Dynamic）                                 │
│ 生命周期：任务期间                                            │
│ 内容：TODO.md、.openclaw/events/、.openclaw/locks/             │
│ 存储位置：项目文件（任务完成后归档到 temp/）                      │
└─────────────────────────────────────────────────────────────┘
                              ↑↓ 任务启动时读取，任务期间持续读写
┌─────────────────────────────────────────────────────────────┐
│ 第 1 层：静态上下文层（Static）                                │
│ 生命周期：项目全周期                                           │
│ 内容：README.md、metadata.json、SKILL.md、.openclawignore      │
│ 存储位置：项目根目录（版本控制）                                 │
└─────────────────────────────────────────────────────────────┘
```

**层次职责**：

| 层次 | 职责 | 读取时机 | 写入时机 | 典型内容 |
|------|------|----------|----------|----------|
| **静态上下文层** | 提供项目基础信息 | Agent 进入项目时 | 项目结构变更后 | README、metadata、协作规范 |
| **动态协作层** | 跟踪任务状态和协作事件 | 每轮对话前 | Agent 行动后 | TODO、events、locks |
| **实时意图层** | 传递当前轮次的具体指令 | 当前轮次 | 当前轮次 | 用户输入、插件提醒 |

**数据流向**：
1. **自上而下**：静态层提供基础上下文 → 动态层补充当前任务 → 实时层传递具体指令
2. **自下而上**：Agent 执行结果 → 更新动态层（TODO、events）→ 可能触发静态层更新（README、metadata）
3. **横向**：Agent 之间通过动态层共享信息（TODO、events、文件系统）

**设计原则**：
- 静态层追求「稳定性」，变更需明确理由（如新增模块）
- 动态层追求「实时性」，每轮对话都可能更新
- 实时层追求「精准性」，只传递当前轮次所需信息

### 3.5 系统状态机（任务生命周期）

任务在系统中经历以下状态，由 TODO.md 记录：

```
用户分配 / Agent 创建
      ↓
【待办】—— 任务已定义，尚未启动
      ↓ Agent 认领（标记 @agent-id）
【进行中】—— Agent 正在执行
      ↓ Agent 自检通过（标记 [SELF_CHECKED]）
【待确认】—— 等待用户确认
      ↓ 用户 [APPROVED]
【已完成】—— 成果归档到 docs/ 或 temp/drafts/
      ↓ 用户 [REJECTED]
【进行中】—— 回到执行状态，Agent 修正
```

**状态转换规则**：
- 用户可随时调整：终止（[USER_BLOCK]）、修改优先级、补充信息
- Agent 可随时举手：写入 TODO.md「待分配（用户协调）」，请求其他 Agent 协助
- 插件不干预状态转换，只提醒 Agent 更新状态

## 4. 插件 Hook 修复方法论

### 4.1 核心原则：Hook 职责对齐

每个 Hook 的注入时机必须与 Agent 在该时机能完成的工作匹配：

| Hook | Agent 能做什么 | 不能做什么 | 插件应该注入什么 | 不应该注入什么 |
|------|---------------|-----------|----------------|--------------|
| `before_prompt_build` | 制定计划、读取上下文、汇报计划 | 检测本轮输出（输出尚未生成） | 当前阶段目标、项目上下文、历史偏差摘要 | 「检查本轮输出是否符合预期」 |
| `after_tool_call` | 评估文件变更、决定下一步 | 改变已发生的工具调用 | 文档更新提醒、协作请求提醒 | 事后纠偏（已太晚） |
| `before_agent_finalize` | 自检、准备汇报 | 重新执行 | 验收检查清单 | 新的执行指令 |
| `agent_end` | 无（Agent 已结束） | 任何需要 Agent 响应的操作 | 仅记录日志、更新索引 | skill 注入（Agent 看不到） |

### 4.2 regulation 修复：条件注入 + 数据供给

**问题**：regulation skill 被实例化但未注入，Agent 没有归因分析所需的 `task.deviations` 数据。

**解决方法**：
1. **触发条件**：`before_prompt_build` + `task.deviations.length > 0`
2. **注入内容**：regulation skill + 未处理偏差摘要（`type`、`description`、`createdAt`）
3. **数据供给**：在 `_buildExecutionContext` 中检测未处理偏差，组装成结构化摘要
4. **Agent 职责**：读取偏差摘要 → 归因分析 → 输出策略更新建议 → 标记偏差为已处理

**设计要点**：
- 不是「每次对话都注入」，而是「有未处理偏差时才注入」
- 注入的是「数据摘要」而非「完整 task 对象」
- Agent 处理完后需标记偏差为 handled，避免重复注入

### 4.3 monitoring 修复：职责重定义

**问题**：monitoring 在 `before_prompt_build` 注入，但要求 Agent「检测上轮输出是否符合预期」，此时输出尚未生成。

**解决方法**：将 monitoring 从「偏差检测器」重定义为「偏差预防提醒 + 自我监控指引」：
1. **注入内容**：当前阶段目标 + 历史偏差列表（最近 3 条）+ 自我监控指引
2. **Agent 行为**：本轮输出后自行对比目标，若发现偏差输出 `[STATUS: revising]`
3. **插件响应**：检测到 `[STATUS: revising]` 后，记录偏差到 `task.deviations`，下次对话注入 regulation

**职责划分**：
- 插件：提供「目标」和「历史偏差」信息
- Agent：自主监控本轮输出，主动标记偏差
- 插件：响应 Agent 的偏差标记，记录到 task 数据结构

### 4.4 working-memory 修复：轻量注入 + 按需查阅

**问题**：working-memory skill 标记 `reference_only`，Agent 在 active 阶段看不到 Session 管理规则。

**解决方法**：
1. **新增 Hook**：在 `working-memory/module.js` 注册 `before_prompt_build`
2. **注入条件**：`task.status === 'active'` 且涉及 session 操作（如 `sessions_spawn`、`sessions_send`）
3. **注入内容**：5 条核心规则（复用、销毁、避免僵尸等），提示完整文档位置
4. **查阅机制**：Agent 需要更多细节时，插件提醒「请读取 working-memory/SKILL.md」

**设计要点**：
- 轻量注入：只给「必须知道的规则」，不给完整文档
- 按需查阅：Agent 需要更多时，通过文件系统读取完整 skill
- 条件触发：只在涉及 Session 操作时注入，避免无关对话的噪声

### 4.5 Session 推荐：插件辅助决策

**问题**：`createSession` 每次生成新 ID，业务规则「同一 taskFamily 优先复用 idle Session」无法实现。

**解决方法**：
1. **新增接口**：`recommendSessions(taskFamily)`，扫描全局索引中的 idle Session
2. **注入时机**：planning skill 注入时，附加推荐列表到上下文
3. **决策权**：Agent 在 Plan 中显式指定复用的 sessionId，插件验证状态（是否 idle）
4. **兜底**：若无推荐或 Agent 不指定，则创建新 Session（保持现有行为）

**职责划分**：
- 插件：提供「推荐信息」（有什么 idle Session）
- Agent：做出「复用决策」（指定 sessionId）
- 插件：执行「状态验证」（确认该 Session 确实 idle）

### 4.6 文件变更审计追踪（after_tool_call 扩展）

**问题**：Agent 修改项目中的 Markdown 文件（如 TODO.md、README.md）后，变更历史分散在各次对话中，后续 Agent 或用户难以快速追溯「谁、何时、改了什么」。

**解决方法**：扩展 `after_tool_call` 已有逻辑，当检测到 `write`/`edit` 工具修改了 `*.md` 文件时，自动追加审计记录到项目事件流。

| 属性 | 定义 |
|------|------|
| **触发时机** | `after_tool_call` + `toolName === 'write'`/`'edit'` + `filePath.endsWith('.md')` |
| **记录位置** | `.openclaw/events/{YYYY-MM-DD}/edits.md`（当日所有文件编辑的聚合日志） |
| **记录格式** | 追加单行：`- {HH:MM} {agent-id} {write/edit} {filePath} — {50字摘要}` |
| **摘要来源** | 工具调用的 `description` 字段（Agent 调用 write/edit 时填写的操作说明） |

**与现有机制的关系**：
- `.openclaw/events/{HH-MM-SS}.md`（4.6 之前定义）：记录单次完整事件（需求→计划→偏差→归因）
- `.openclaw/events/{YYYY-MM-DD}/edits.md`（本项新增）：仅记录文件编辑审计，不重复事件内容
- 两者互补：edits.md 提供「文件维度」的变更历史，事件文件提供「任务维度」的完整上下文

**代码实现位置**：`src/metacognition/module.js` 中 `_registerToolResult()` 或 `src/common/adapters/hook.js` 中新增方法

**验收标准**：
1. Agent 修改 `TODO.md` 后，`.openclaw/events/2026-05-08/edits.md` 出现新行
2. 同一轮对话中多次修改同一文件，只记录最后一次
3. 不追踪非 `.md` 文件（代码文件由 git 管理）

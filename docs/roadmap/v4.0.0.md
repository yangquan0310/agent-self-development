# v4.0.0 Roadmap: Project Context Layer & Multi-Agent Collaboration

> **核心目标**：建立「项目上下文层」，使多 Agent 能在同一项目中协作。
> **状态**：active
> **创建时间**：2026-05-08
> **预计完成**：2026-05-15

---

## 1. 问题诊断

### 问题1：项目没有标准化的协作基础设施
**现状**：不同 Agent 接手同一项目时，无法快速理解项目结构和当前状态。
**根因**：没有定义标准的项目级文件系统协作协议，Agent 不知道文件该放哪、怎么找其他 Agent 的成果、如何声明自己的编辑意图。
**影响**：每次新项目接入都需要重新探索，协作效率低。

### 问题2：缺少系统化的协作方法论
**现状**：Agent 各自为政，用户需要在多个 Agent 之间手动协调。
**根因**：没有定义 Agent 如何「举手」请求协助、如何向用户汇报进度、插件应该在什么时机督促 Agent。
**影响**：Agent 执行任务时沉默执行，用户不知道进度；Agent 遇到困难时死等用户发现。

### 问题3：插件 Hook 注入机制与职责不匹配
**现状**：
- regulation skill 被实例化但从未注入，Agent 无法获得归因分析所需的上下文数据
- monitoring 在 `before_prompt_build` 注入，但此时本轮输出尚未生成，无法做「输出 vs 预期」对比
- working-memory 标记为 `reference_only`，Agent 在 active 阶段看不到 Session 管理规则
**根因**：Hook 的 `injected_at` 与 Agent 在该时机能完成的工作不匹配。
**影响**：Agent 被 skill 告知要做某事，但插件从未提供执行所需的数据或时机。

---

## 2. 目标凝练

| 目标 | 对应问题 | 成功标准 |
|------|---------|----------|
| **建立项目上下文层（Project Context Layer）** | 问题1 | 任意项目接入后，Agent 可通过标准化文件系统协作 |
| **设计人机协同协作系统** | 问题2 | 用户分配→Agent执行→举手请求→插件督促→用户确认，形成闭环 |
| **修复插件 Hook 职责对齐** | 问题3 | 每个 skill 在正确的时机注入，Agent 获得所需数据 |

## 3. 解决方法：系统方法论设计

### 3.1 系统定义：双系统平行架构

v4.0.0 采用**双系统平行架构**：

```
┌─────────────────────────────────────────────────────────────┐
│              Agent 自行行动系统（文件系统）                    │
│  计划 → 监控 → 调节 → 发展                                   │
│  Agent 是唯一写入者：写入 README / TODO / events / tasks     │
│  Agent 通过读取文件获取上下文，自主决策推进任务                │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼ 插件读取（Hooks）
┌─────────────────────────────────────────────────────────────┐
│              史官系统（插件记录系统）                          │
│  插件只读取项目文件，将内容移动到系统层                        │
│  Memory（SQLite）/ Log                                       │
│  【占位符】State / Flow / 心跳统计 — 待后续按需实现            │
│  系统层目前仅用于 Memory 归档和日志；查询/心跳为占位符         │
└─────────────────────────────────────────────────────────────┘
```

**双系统关系**：
- **Agent 是项目文件系统的唯一写入者**：Agent 直接写入 `tasks/{runId}.json`、事件文件、TODO.md 等所有项目文件。插件不写入项目文件，只读取。
- **插件是项目文件的读取者 + 系统层的写入者**：插件通过 Hook 读取 Agent 写入的项目文件，将关键状态提取并记录到系统层（SQLite/JSON）。系统层数据目前仅用于 Memory 归档和日志记录，查询/统计为占位符。**不直接驱动 Agent 行为**。
- **上下文来源**：Agent 的上下文来自**文件系统**（`tasks/{runId}.json`、事件文件、TODO.md），而非系统层的 SQLite。插件目前仅将已完成任务归档到系统层 Memory、记录运行日志；历史查询和心跳监控为占位符。

**项目上下文层定义**：位于 OpenClaw 会话层之下的持久化协作层，通过标准化的项目目录结构和文件协议，使多个独立的 Agent 能够在同一项目中共享上下文、协作完成任务。

**核心特性**：
- **持久化**：数据存储在项目文件中，不依赖 Session 内存
- **标准化**：所有项目遵循相同的目录结构和文件格式
- **可发现**：Agent 进入项目后，通过读取标准文件即可理解项目状态
- **无共享内存**：Agent 之间不通过 `sessions_send` 通信，只通过文件系统读写协作
- **史官并行**：插件同步记录到系统层，但记录不影响 Agent 的自主决策

### 3.2 系统元件（Components）

项目上下文层由以下核心元件组成：

#### 元件1：四文件契约（The Four-File Covenant）
每个项目必须具备的四个核心文件，作为 Agent 的「上下文基线」：

| 元件 | 职责 | 内容 | 维护者 |
|------|------|------|--------|
| **README.md** | 项目总览 | 项目定位、目录结构说明、关键文件索引、快速开始指南 | Agent / 用户 |
| **metadata.json** | 机器可读架构 | 模块列表、技能列表、Agent 能力定义、协作模式配置 | Agent |
| **SKILL.md**（项目级） | 操作手册 | 项目特有的工作流程、工具使用规范、输出格式要求 | Agent |
| **TODO.md** | 进度看板 | 当前任务状态、进行中任务、待确认任务、已完成任务 | Agent / 用户 |

**设计原则**：
- README 是「人类视角」的总览，metadata.json 是「机器视角」的结构，两者互补
- SKILL.md 是「过程规范」，TODO.md 是「状态跟踪」，两者共同支撑协作执行
- 四文件必须位于项目根目录，Agent 进入项目时优先读取

#### 元件2：.openclaw/ 元数据层
位于项目根目录下的隐藏目录，存储协作过程中产生的元数据：

| 子目录 | 职责 | 结构 | 读写规则 |
|--------|------|------|----------|
| **events/** | 事件流 | 按天分文件夹：`events/{YYYY-MM-DD}/` | Agent 只写入 |
| **locks/** | 并发控制 | 单文件：`locks/{文件路径替换-为-}.json` | Agent 创建/删除 |
| **decisions/** | 决策存档 | 单文件：`decisions/{YYYYMMDD-HHMM}-标题.md` | Agent 写入 |
| **tasks/** | 任务文件索引 | JSON：`tasks/{runId}.json` + 索引：`tasks/INDEX.md` | Agent 读写 |

**events/ 详细设计**：
- **目录结构**：`.openclaw/events/{YYYY-MM-DD}/`
- **文件命名**：`{HH-MM-SS}.md`（精确到秒，单文件记录完整事件）
- **文件内容**：7 个部分（元信息 → 计划 → 执行 → 变更记录 → 偏差 → 归因 → 结果，单文件闭环）
  ```markdown
  # 事件 {HH-MM-SS}
  
  > **时间**：{YYYY-MM-DD HH:MM:SS}
  > **触发者**：{user | agent-id | plugin}
  
  ---
  
  ## 1. 元信息（Metadata）
  - runId: {uuid}
  - agentId: {agent-id}
  - role: {primary | subagent}
  
  ## 2. 计划（Plan）
  {制定的执行计划：步骤、验收标准、预估时间}
  
  ## 3. 执行（Execution）
  {实际执行过程、完成的工作、产出的文件}
  
  ## 4. 变更记录（ChangeLog）
  - {HH:MM} {agent-id} {write|edit} {filePath} — {50字摘要}
  
  ## 5. 偏差（Deviation）
  {执行中发现的偏差}
  - 偏差类型：{type}
  - 描述：{具体描述}
  - 影响评估：{影响范围}

  **偏差类型规范（v4.0.0 统一）**：

  | 类型 | 定义 | 典型场景 |
  |------|------|----------|
  | `output_mismatch` | 实际输出与 Plan 预期不符 | 代码未按设计实现、文档遗漏关键章节 |
  | `doc_lag` | 文档/代码不同步 | 代码已改但 README/SKILL.md 未更新 |
  | `context_loss` | 文件系统上下文丢失 | Agent 未读取历史文件、重复劳动、遗漏前置文件 |
  | `file_mismatch` | 文件路径或内容错误 | 写入错误路径、覆盖他人文件、文件格式不符规范 |
  | `other` | 其他未分类偏差 | 用户临时变更需求、外部依赖问题 |
  
  ## 6. 归因（Attribution）
  {偏差产生的原因分析}
  - 根本原因：{分析结果}
  - 影响评估：{影响范围}
  - 策略更新：{后续调整建议}
  
  ## 7. 结果（Outcome）
  {事件最终状态：完成 / 修正 / 放弃}
  ```
- **设计原则**：任务创建时由 Agent 同步创建事件文件，作为该任务的持续记录；任务推进过程中 Agent 向其中追加内容（元信息→计划→执行→变更记录→偏差→归因→结果）
- **Agent 行为**：Agent 创建新事件文件；在已有事件文件中追加新章节（如偏差、归因）；任务完成后 Agent 将事件文件归档到 `temp/events/`
- **插件行为**：插件读取事件文件，将内容转存到系统层 Memory SQLite（`eventlogs` 表）【占位符：目前仅归档，供后续历史查询和心跳监控使用】
- **示例**：`.openclaw/events/2026-05-08/18-30-00.md` — Agent 在任务启动时创建，任务完成后归档

**tasks/ 详细设计（v4.0.0 变更）**：
- **职责**：记录每个 task 的关联文件路径及负责 Agent，替代原有的 Session 追踪
- **文件命名**：`tasks/{runId}.json`（与 task.runId 一一对应）
- **文件内容**：
  ```json
  {
    "runId": "uuid",
    "status": "active",
    "agentId": "main",
    "role": "primary",
    "createdAt": "ISO-8601",
    "updatedAt": "ISO-8601",
    "files": [
      {"path": "manuscripts/plan.md", "agentId": "main", "role": "primary", "type": "draft"},
      {"path": "src/index.js", "agentId": "coder", "role": "subagent", "type": "artifact"}
    ]
  }
  ```
- **字段说明**：
  - `agentId`：负责该任务的主 Agent ID
  - `role`：`primary`（主代理）或 `subagent`（子代理）
  - `files[].agentId`：产出该文件的 Agent ID
  - `files[].role`：该 Agent 相对于本任务的角色
  - `files[].type`：`draft`（草稿，位于 manuscripts/）或 `artifact`（定稿，位于 docs/ 或 src/）
- **索引文件**：`tasks/INDEX.md` 按日期分组列出所有任务摘要，供人类和 Agent 快速浏览
- **与 events/ 的区别**：events 是时间线叙事，tasks 是任务维度的文件索引
- **写入者**：Agent 负责写入和更新 `tasks/{runId}.json`（记录自己产出的文件路径、agentId、role）
- **插件行为**：插件读取 `tasks/{runId}.json` 供自身使用（如文件上下文注入）；同步到系统层 State 为【占位符】

#### 元件3：业务目录层
项目实际的业务内容存储目录：

| 目录 | 职责 | 访问规则 |
|------|------|----------|
| **uploads/** | 用户上传的原始材料 | Agent 只读，不可写入 |
| **manuscripts/** | Agent 工作草稿（进行中、未确认） | Agent 读写 |
| **docs/** | 定稿（用户已确认的成果） | Agent 可读写（写入前需获得用户 [APPROVED]） |
| **knowledge/** | 项目积累的知识（笔记和综述） | Agent 读写 |
| **temp/** | 临时文件和归档草稿 | Agent 读写 |

**设计原则**：
- uploads/ 是「输入层」，用户提供的原始材料
- manuscripts/ 是「工作层」，Agent 的草稿和中间产出
- docs/ 是「输出层」，经用户确认的最终成果
- 文件从 manuscripts/ 到 docs/ 必须经过用户确认（[APPROVED]）

#### 元件4：插件督促层（史官观察层）

由 `agent-self-development` 插件提供的 Hook 注入机制。**插件是史官，不是指挥官**：
- **注入侧**：通过 Hook 向 Agent 注入 skill 提醒，督促 Agent 按规范行动
- **读取侧**：通过 Hook 读取 Agent 写入的项目文件；仅 Memory 归档和日志为必需，其他系统层写入为占位符
- **不写入项目文件**：插件不修改、不创建项目文件系统中的任何文件（`.openclaw/`、业务目录均不可写）
- **不控制**：插件不替 Agent 决策，只提醒和读取

| 时机 | 注入元件 | 职责（提醒 Agent） | 职责（史官读取+系统层记录） |
|------|----------|-------------------|---------------------------|
| `before_prompt_build`（任务启动） | planning skill + 项目上下文 | 督促 Agent 制定计划、读取文件系统上下文 | — |
| `before_prompt_build`（执行中） | monitoring skill | 督促 Agent 汇报进度、自我监控 | — |
| `after_tool_call`（文件变更后） | project-context skill | 提醒 Agent 更新文档或举手请求协助 | 读取事件文件变更记录 → 系统层日志；读取 `tasks/{runId}.json` 供注入使用 |
| `before_agent_finalize`（完成前） | monitoring skill | 督促 Agent 自检、请求用户确认 | 解析状态标记 → 更新 task.status |
| `agent_end`（任务结束） | — | — | 读取事件文件 → 系统层 Memory（任务归档）；读取 `tasks/{runId}.json` → 系统层 Memory（任务归档） |

**设计原则**：
- 插件不替 Agent 决策，只「提醒」和「读取」
- 插件不写入项目文件系统，Agent 是项目文件的唯一写入者
- 注入的内容必须是 Agent 在该时机能执行的操作（如制定计划、汇报进度）
- 避免注入需要「未来数据」的内容（如本轮尚未生成的输出）
- 系统层记录与文件系统操作平行，不阻塞 Agent 的文件读写

#### 元件5：.openclawignore 可见性控制
定义 Agent 对项目文件的可见性边界：

| 规则类型 | 示例 | Agent 行为 |
|----------|------|-----------|
| 完全隐藏 | `.env`, `.git/`, `node_modules/` | 对 Agent 不存在，提问时回答"无此文件" |
| 只读 | `uploads/` | 可读但不可写，写入操作被拒绝 |
| 透明 | `.openclaw/locks/` | 锁文件对 Agent 透明，冲突检测由插件处理 |

### 3.3 系统交互（Interaction Protocol）

系统由三类参与者组成，它们通过文件系统和 Hook 注入交互：

```
参与者：
  ├─ 用户（Human）
  ├─ Agent（执行者，如 main / writer / coder）
  └─ 插件（Plugin，如 agent-self-development）

交互媒介：
  ├─ 文件系统（持久化协作层）
  └─ Hook 注入（实时提醒层）
```

#### 交互1：用户 → Agent（任务分配）

**协议**：用户通过对话直接分配任务给特定 Agent
**信息流向**：用户描述需求 → Agent 读取项目上下文 → Agent 理解任务
**文件系统影响**：Agent 在 TODO.md 标记任务为「进行中」
**约束**：用户根据 Agent 特性分配任务（如 "main，你擅长系统配置，初始化项目"）

#### 交互2：Agent → 文件系统（工作产出）

**协议**：Agent 将产出写入 manuscripts/，完成自检后请求用户确认
**信息流向**：Agent 工作 → 写入 manuscripts/ → 在 TODO.md 标记「待确认」
**文件系统影响**：
- manuscripts/ 新增文件
- TODO.md 任务状态变更
- .openclaw/events/ 追加工作记录
**约束**：Agent 不可直接写入 docs/，必须经过用户确认

#### 交互3：Agent → 用户（举手请求）

**协议**：Agent 发现需要其他 Agent 能力时，写入 TODO.md 并汇报用户
**信息流向**：
1. Agent A 继续执行自己擅长的部分（不阻塞）
2. Agent A 在 TODO.md「待分配（用户协调）」写入子任务
3. Agent A 向用户汇报：「我擅长 X，但发现需要 Y。建议分配给擅长 Y 的 Agent B。我继续处理 X。」
4. 用户收到后，将子任务分配给 Agent B
**文件系统影响**：TODO.md 新增「待分配」任务项

#### 交互4：插件 → Agent（督促提醒）

**协议**：插件作为史官，通过 Hook 在关键时机注入提醒内容。插件**不读取系统层 SQLite** 来为 Agent 提供上下文，而是提醒 Agent 去**读取文件系统**获取上下文。插件**不写入项目文件**。
**信息流向**：
- 任务启动时：注入「请制定执行计划，读取 `metadata.json` 和 `TODO.md` 了解项目上下文；创建任务事件文件」
- 执行中时：注入「请汇报当前进度，读取 `tasks/{runId}.json` 了解已涉及的文件」
- 文件变更后：注入「请确认是否需要协助，检查 `.openclaw/locks/` 避免冲突；更新 `tasks/{runId}.json` 和当前任务事件文件的变更记录章节」
- 完成前：注入「请自检并请求用户确认，更新 TODO.md 和事件文件」
- 偏差检测时：注入「请输出 [STATUS: revising]，在事件文件中记录偏差」
- 归因分析时：注入「请按 regulation skill 分析偏差原因，基于事件文件中的偏差数据」
**约束**：
- 插件只提醒，不替 Agent 决策；Agent 可忽略提醒（但需承担后果）
- **Agent 是项目文件系统的唯一写入者**：Agent 将完整上下文（计划/偏差/归因）写入 `.openclaw/events/{YYYY-MM-DD}/{HH-MM-SS}.md`
- **插件只读取项目文件**：插件读取 Agent 写入的文件；仅 Memory 归档和日志写入系统层，其他为占位符。不向 Agent 暴露系统层数据

#### 交互5：Agent ↔ Agent（文件系统协作）

**协议**：多个 Agent 通过读写共享文件协作，不通过 `sessions_send`
**信息流向**：
- Agent A 将中间成果写入 manuscripts/ 或 knowledge/notes/
- Agent B 读取同一文件，继续工作
- 若编辑同一文件，通过 .openclaw/locks/ 检测冲突
**约束**：
- 禁止 Agent 之间直接对话（`sessions_send`）
- 所有协作必须通过文件系统
- 冲突时由用户裁定或 Agent 协商

#### 交互6：用户 → 文件系统（最终确认）

**协议**：用户通过标记确认 Agent 成果
**信息流向**：用户检查 manuscripts/ → 输出 [APPROVED] 或 [REJECTED]
**文件系统影响**：
- [APPROVED]：文件从 manuscripts/ 移到 docs/，任务移到「已完成」
- [REJECTED]：任务回到「进行中」，Agent 修正

### 3.4 系统组织（Architecture）

项目上下文层采用**三层架构 + 史官并行层**组织：

```
┌─────────────────────────────────────────────────────────────┐
│ 第 3 层：实时意图层（Ephemeral）                              │
│ 生命周期：单轮对话                                              │
│ 内容：用户输入、Agent 输出、插件注入的提醒                       │
│ 存储位置：Session 内存（不持久化）                              │
└─────────────────────────────────────────────────────────────┘
                              ↑↓ 每轮对话读写
┌─────────────────────────────────────────────────────────────┐
│ 第 2 层：动态协作层（Dynamic）← Agent 的主上下文来源            │
│ 生命周期：任务期间                                            │
│ 内容：TODO.md、.openclaw/events/、.openclaw/tasks/、.openclaw/locks/ │
│ 存储位置：项目文件（任务完成后归档到 temp/）                      │
└─────────────────────────────────────────────────────────────┘
                              ↑↓ 任务启动时读取，任务期间持续读写
┌─────────────────────────────────────────────────────────────┐
│ 第 1 层：静态上下文层（Static）                                │
│ 生命周期：项目全周期                                           │
│ 内容：README.md、metadata.json、SKILL.md、.openclawignore      │
│ 存储位置：项目根目录（版本控制）                                 │
└─────────────────────────────────────────────────────────────┘

【史官并行层】与上述三层平行运行，通过 Hook 观察记录：
- State（task JSON）/ Flow / Memory（SQLite）/ Log
- 不直接为 Agent 提供上下文；目前仅 Memory 归档和日志为必需，查询/心跳统计为占位符
```

**层次职责**：

| 层次 | 职责 | 读取时机 | 写入时机 | 典型内容 |
|------|------|----------|----------|----------|
| **静态上下文层** | 提供项目基础信息 | Agent 进入项目时 | 项目结构变更后 | README、metadata、协作规范 |
| **动态协作层** | 跟踪任务状态、文件索引和协作事件 | 每轮对话前 | Agent 行动后 | TODO、events、tasks、locks |
| **实时意图层** | 传递当前轮次的具体指令 | 当前轮次 | 当前轮次 | 用户输入、插件提醒 |

**数据流向**：
1. **自上而下**：静态层提供基础上下文 → 动态层补充当前任务 → 实时层传递具体指令
2. **自下而上**：Agent 执行结果 → 更新动态层（TODO、events）→ 可能触发静态层更新（README、metadata）
3. **横向**：Agent 之间通过动态层共享信息（TODO、events、文件系统）

**设计原则**：
- 静态层追求「稳定性」，变更需明确理由（如新增模块）
- 动态层追求「实时性」，每轮对话都可能更新
- 实时层追求「精准性」，只传递当前轮次所需信息

### 3.5 系统状态机（任务生命周期）

任务在系统中经历以下状态，由 TODO.md 记录：

```
用户分配 / Agent 创建
      ↓
【待办】—— 任务已定义，尚未启动
      ↓ Agent 认领（标记 @agent-id）
【进行中】—— Agent 正在执行
      ↓ Agent 自检通过（标记 [SELF_CHECKED]）
【待确认】—— 等待用户确认
      ↓ 用户 [APPROVED]
【已完成】—— 成果归档到 docs/ 或 temp/drafts/
      ↓ 用户 [REJECTED]
【进行中】—— 回到执行状态，Agent 修正
```

**状态转换规则**：
- 用户可随时调整：终止（[USER_BLOCK]）、修改优先级、补充信息
- Agent 可随时举手：写入 TODO.md「待分配（用户协调）」，请求其他 Agent 协助
- 插件不干预状态转换，只提醒 Agent 更新状态

### 3.6 插件 Hook 注入路径（Skill 分发图）

> **史官原则**：插件是 Agent 自行行动系统的旁观者，只通过 Hook 观察文件系统中的变化并记录到系统层。插件注入的 skill 是「提醒」而非「指令」，Agent 自行决策是否遵循。
>
> **上下文来源**：Agent 的上下文来自**文件系统**（`tasks/{runId}.json`、TODO.md、事件文件），而非系统层的 SQLite。系统层数据目前仅用于 Memory 归档和日志记录；查询/心跳统计为占位符。

v4.0.0 共注册 **7 个 Hooks**，其中 **4 个为决策/注入型**（可返回系统上下文或 action），**3 个为纯观察型**（仅做副作用）。按 task 生命周期分 9 个阶段注入：

#### 总体概览

| Hook | 类型 | 触发时机 | 职责 | 条件 |
|------|------|---------|------|------|
| `before_prompt_build` | 决策/注入 | 每轮对话构建 prompt 前 | 按 task.status 分发 skill | 无条件 |
| `before_tool_call` | 纯观察 | Agent 调用工具前 | 记录子代理创建意图 | `sessions_spawn`/`agent`/`subagent` |
| `after_tool_call` | 纯观察 | Agent 调用工具后 | 记录工具错误、审计文件变更（读取事件文件变更记录 → 系统层日志） | 无条件 |
| `llm_output` | 纯观察 | LLM 输出后 | 聚合流式输出 | 无条件 |
| `before_agent_finalize` | 决策/注入 | Agent 输出完成、准备 finalize 前 | 解析 [STATUS]、检测 [NEED_PLAN]、质量检查 | 无条件 |
| `agent_end` | 纯观察 | Agent 结束 | 归档 task、清理资源 | 无条件 |
| `heartbeat_prompt_contribution` | 决策/注入 | 心跳监控回合 | 注入状态统计 | 异步 |

#### Skill 注入映射表

| task.status | 注入 Skill | 注入内容 | 目的 |
|-------------|-----------|----------|------|
| 无 task | `planning`（评估） | 任务评估流程、复杂度判断标准 | 让 Agent 决定是否需要制定 Plan |
| `draft` | `planning`（制定） | Plan 模板、阶段划分规则、文件上下文提示 | 让 Agent 制定完整 Plan |
| `pending_approval` | `planning`（反馈） | 用户反馈处理指南、状态转换规则 | 让 Agent 处理确认/修改/取消 |
| `active` | `monitoring` + 执行上下文 + WM文件上下文(条件) + regulation(条件) | 当前阶段目标、历史偏差、文件列表、未处理偏差 | 让 Agent 自主执行并监控偏差 |
| `revising` | `planning`（修订） | 修订原因、当前 Plan 快照 | 让 Agent 重新制定 Plan |
| `completed` | 无（agent_end 纯观察） | — | 插件自动归档，不注入 |

#### 关键设计原则

1. **单一入口**：所有 skill 注入唯一入口是 `before_prompt_build`，避免多 Hook 同时注入造成冲突
2. **条件注入**：regulation 和 WM 文件上下文只在有数据时才注入，避免空提醒疲劳
3. **纯观察不返回**：`llm_output` / `agent_end` / `before_tool_call` / `after_tool_call` 禁止返回 `prependSystemContext` 或 `action`
4. **文件驱动**：执行阶段的核心上下文从「Session 内存」转向「文件系统读取」（`tasks/{runId}.json` + `manuscripts/` + `docs/`）
5. **史官并行**：插件记录系统（State/Memory）与文件系统平行运行，只记录不干预；Agent 的上下文永远来自文件系统，而非 SQLite
6. **双系统不交叉**：Agent 不直接读取系统层 SQLite，插件不直接修改 Agent 的文件（除 `after_tool_call` 自动审计外）

## 4. 插件 Hook 修复方法论

### 4.1 核心原则：Hook 职责对齐

每个 Hook 的注入时机必须与 Agent 在该时机能完成的工作匹配：

| Hook | Agent 能做什么 | 不能做什么 | 插件应该注入什么 | 不应该注入什么 |
|------|---------------|-----------|----------------|--------------|
| `before_prompt_build` | 制定计划、读取文件系统上下文、汇报计划 | 检测本轮输出（输出尚未生成） | 当前阶段目标（来自 State）、文件上下文（来自 `tasks/{runId}.json`）、历史偏差（来自事件文件） | 「检查本轮输出是否符合预期」 |
| `after_tool_call` | 评估文件变更、决定下一步 | 改变已发生的工具调用 | 文档更新提醒、协作请求提醒 | 事后纠偏（已太晚） |
| `before_agent_finalize` | 自检、准备汇报 | 重新执行 | 验收检查清单 | 新的执行指令 |
| `agent_end` | 无（Agent 已结束） | 任何需要 Agent 响应的操作 | 仅记录日志、更新索引 | skill 注入（Agent 看不到） |

### 4.2 regulation 修复：条件注入 + 数据供给

**问题**：regulation skill 被实例化但未注入，Agent 没有归因分析所需的事件文件偏差数据。

**解决方法**：
1. **触发条件**：`before_prompt_build` + 当前任务的事件文件中存在未处理偏差（"偏差"章节已写入但无"归因"章节）
2. **注入内容**：regulation skill + 事件文件中的偏差摘要（`type`、`description`）
3. **数据供给**：在 `_buildExecutionContext` 中读取 `.openclaw/events/{YYYY-MM-DD}/{HH-MM-SS}.md`，提取「偏差」章节内容
4. **Agent 职责**：读取偏差摘要 → 归因分析 → 在事件文件中追加「归因」章节 → 输出策略更新建议

**设计要点**：
- 不是「每次对话都注入」，而是「事件文件中有未处理偏差时才注入」
- 注入的是「事件文件中的偏差摘要」而非「完整 task 对象」
- Agent 完成归因后，在事件文件中追加「归因」章节，插件通过检测该章节存在来判断偏差已处理

### 4.3 monitoring 修复：职责重定义

**问题**：monitoring 在 `before_prompt_build` 注入，但要求 Agent「检测上轮输出是否符合预期」，此时输出尚未生成。

**解决方法**：将 monitoring 从「偏差检测器」重定义为「偏差预防提醒 + 自我监控指引」：
1. **注入内容**：当前阶段目标 + 历史偏差列表（最近 3 条，从事件文件读取）+ 自我监控指引
2. **Agent 行为**：本轮输出后自行对比目标，若发现偏差输出 `[STATUS: revising] [REASON: xxx]`
3. **插件响应**：检测到 `[STATUS: revising]` 后，更新 `task.status = 'revising'`；由 Agent 在事件文件中手动记录偏差；下次对话前扫描事件文件，如有未处理偏差则注入 regulation

**职责划分**：
- 插件：提供「目标」和「历史偏差」信息
- Agent：自主监控本轮输出，主动标记偏差
- 插件：响应 Agent 的偏差标记，记录到 task 数据结构

### 4.4 working-memory 修复：文件系统上下文注入

**问题**：working-memory skill 标记 `reference_only`，Agent 在 active 阶段看不到上下文管理规则。v3.x 依赖 Session 内存复用保持上下文，但 Session 上下文在多 Agent 协作场景下不可行。

**解决方法**：将 WM 从「Session 管理」重定义为「文件系统上下文管理」：
1. **新增 Hook**：在 `working-memory/module.js` 注册 `before_prompt_build`
2. **注入条件**：`task.status === 'active'` 且 Agent 需要上下文保持（如多轮对话、子代理协作）
3. **注入内容**：
   - 当前 task 的关联文件列表（从 `tasks/{runId}.json` 读取）
   - 5 条核心规则：
     1. 上下文通过文件系统保持，不依赖 Session 内存
     2. 每次写入文件后，Agent 自行更新 `tasks/{runId}.json`（Agent 是唯一写入者）
     3. 子代理产出通过文件路径关联到主任务，不追踪 Session ID
     4. 如需了解任务涉及的所有文件，请读取 `tasks/{runId}.json`
     5. 如需查看所有任务索引，请读取 `tasks/INDEX.md`
4. **查阅机制**：Agent 需要更多细节时，插件提醒「请读取 tasks/{runId}.json」

**设计要点**：
- 上下文保持从「内存复用」转向「文件读取」
- 插件自动维护 `tasks/{runId}.json`，Agent 只需读取
- 不再维护 `working_memory:active_sessions` 全局索引

### 4.5 文件上下文提示：替代 Session 推荐

**问题**：v3.x 的 `recommendSessions(taskFamily)` 基于 idle Session 复用，但 Session 内存上下文不可行，需要新的上下文保持机制。

**解决方法**：移除 Session 推荐，改为「历史文件上下文提示」：
1. **新增接口**：`getTaskFilePaths(runId)`，从 `tasks/{runId}.json` 读取该任务关联的所有文件路径
2. **注入时机**：`before_prompt_build` + planning skill 注入时，若该任务已有历史文件，附加文件列表到上下文
3. **Agent 行为**：根据文件列表选择性读取相关文件以保持上下文
4. **兜底**：若该任务无历史文件（新任务），则正常开始，不附加文件列表

**职责划分**：
- 插件：读取 `tasks/{runId}.json`，提供「该任务已涉及的文件列表」（通过 `before_prompt_build` 注入）
- Agent：决定读取哪些文件来保持上下文；在每次写入文件后，自行更新 `tasks/{runId}.json`（Agent 是唯一写入者）

### 4.6 文件变更审计追踪（after_tool_call 扩展）

**问题**：Agent 修改项目中的 Markdown 文件（如 TODO.md、README.md）后，变更历史分散在各次对话中，后续 Agent 或用户难以快速追溯「谁、何时、改了什么」。

**解决方法**：Agent 在每次使用 `write`/`edit` 工具修改 `*.md` 文件后，自行在当前任务的事件文件中追加「变更记录」章节条目。插件在 `after_tool_call` 中读取事件文件的变更记录章节，将审计记录转存到系统层日志。

**事件文件结构**（一个任务一个文件，含变更记录章节）：

```markdown
## 元信息
- runId: xxx
- agentId: xxx
- role: xxx
- createdAt: 2026-05-08T18:30:00

## 计划
...

## 变更记录
- 18:35 agent-1 write TODO.md — 添加 P1 任务到 TODO 列表
- 18:42 agent-1 edit docs/reference/architecture.md — 更新双系统架构图

## 偏差
...

## 归因
...

## 结果
...
```

| 属性 | 定义 |
|------|------|
| **触发时机** | Agent 调用 `write`/`edit` 工具后，自行追加记录 |
| **写入者** | Agent（唯一写入者） |
| **记录位置** | 当前任务的事件文件（`.openclaw/events/{YYYY-MM-DD}/{HH-MM-SS}.md`）「变更记录」章节 |
| **记录格式** | 追加单行：`- {HH:MM} {agent-id} {write|edit} {filePath} — {50字摘要}` |
| **摘要来源** | 工具调用的 `description` 字段（Agent 调用 write/edit 时填写的操作说明） |
| **插件行为** | `after_tool_call` 读取事件文件「变更记录」章节，将新记录转存到系统层日志 |

**与现有机制的关系**：
- 事件文件是**任务的唯一载体**：一个任务对应一个事件文件（`.openclaw/events/{YYYY-MM-DD}/{HH-MM-SS}.md`）
- 事件文件包含完整上下文：元信息 → 计划 → 变更记录 → 偏差 → 归因 → 结果
- 插件通过 `after_tool_call` 读取事件文件中的变更记录章节，转存到系统层日志，作为「文件维度」的归档索引

**代码实现位置**：`src/working-memory/module.js` 的 `onAfterToolCall()` 中扩展

**验收标准**：
1. Agent 修改 `TODO.md` 后，当前任务事件文件的「变更记录」章节出现新行
2. 同一轮对话中多次修改同一文件，只记录最后一次
3. 不追踪非 `.md` 文件（代码文件由 git 管理）

    6. **归因（Attribution）**：根本原因、影响评估、策略更新
    7. **结果（Outcome）**：最终状态（完成/修正/放弃）

## 6. 版本边界（本版本不做）

| 范围 | 说明 | 原因 |
|------|------|------|
| **系统层 State/Flow [占位符]** | 系统层 State（task 索引）、Flow（工作流状态）当前无消费者 | 仅 Memory 归档和日志为必需，State/Flow/心跳统计待后续按需实现 |
| **系统级 task JSON 废弃** | 系统级 `~/.openclaw/state/.../tasks/{runId}.json` 不再作为 task 主存储 | Agent 直接写入项目级 `.openclaw/tasks/{runId}.json`；插件仅将已完成任务归档到系统层 Memory，其他转存为占位符 |
| **系统层 Memory 数据库** | 仅用于**已完成任务**的 Memory 归档；历史查询为占位符 | 任务完成后，插件读取项目级 `tasks/{runId}.json` 和事件文件归档到系统层 Memory；活跃任务只在项目级 JSON 中 |
| **OpenClaw 核心 API** | 不新增 Hook 类型、不修改 Gateway 事件总线 | 仅在现有 Hook 体系内做职责对齐 |
| **通用基础设施** | 项目上下文层仅服务本插件管理的项目，不作为所有 OpenClaw 插件的通用标准 | 聚焦本插件场景，避免过度设计 |
| **自动冲突解决** | `.openclaw/locks/` 只检测冲突并提醒，不自动合并 | 冲突裁定权归用户 |
| **代码文件审计** | 只追踪 `.md` 文件，不追踪 `.js`/`.json` 等代码文件 | 代码变更由 git 管理 |
| **双系统边界** | Agent 不直接读取系统层 SQLite；插件不写入项目文件系统 | 保持文件系统与插件记录系统的严格平行独立性 |

## 7. 风险与应对

| 风险 | 影响 | 可能性 | 应对策略 |
|------|------|--------|----------|
| **Skill 文件膨胀** | Agent 上下文过长，注意力分散 | 中 | 轻量注入（只给核心规则），按需查阅完整文档；monitoring 只注入最近 3 条偏差 |
| **Agent 忽略插件提醒** | 协作协议形同虚设，Agent 仍按旧习惯执行 | 中 | 所有提醒附带「不执行后果」说明；`before_agent_finalize` 检测 [STATUS] 标记缺失时触发 revise |
| **多 Agent 同时编辑冲突** | 文件覆盖、状态丢失 | 低 | `.openclaw/locks/` 机制 + Agent 编辑前自检锁文件 |
| **P0 模板不适用所有项目** | 四文件契约在某些项目类型（如纯前端、纯后端）中冗余 | 中 | 模板提供「最小可用」版本，Agent 按项目类型选择性填充；metadata.json 的 `type` 字段驱动差异化 |
| **regulation 注入时机过晚** | 偏差已累积多轮才触发归因 | 低 | 偏差一产生即记录到事件文件，下次 `before_prompt_build` 扫描事件文件立即注入 |
| **tasks/{runId}.json 未及时更新** | Agent 不知道已有上下文文件，重复劳动或遗漏 | 中 | planning skill 和 monitoring skill 提醒 Agent 每次写入文件后更新 `tasks/{runId}.json`；Agent 执行前必读 `tasks/{runId}.json` |
| **项目初始化协议被跳过** | Agent 直接进入执行，不创建项目上下文层 | 中 | planning skill 在评估阶段增加「是否需要初始化项目上下文」判断；未初始化项目注入项目上下文缺失警告 |

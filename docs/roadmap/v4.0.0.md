# v4.0.0 Roadmap: Project Context Layer & Multi-Agent Collaboration

> **核心目标**：建立「项目上下文层」，使多 Agent 能在同一项目中协作。
> **设计哲学**：文档即契约 —— README 是项目总览，metadata.json 是机器可读的架构，SKILL.md 是操作手册，TODO.md 是进度看板。
> **协作模式**：
> - **归档/记录 Agent**：维护项目文档，确保「代码 ↔ 文档」同步
> - **业务 Agent**：通过标准化文档快速理解项目，执行具体任务
> - **所有 Agent**：共享同一套项目上下文，减少沟通成本
> 
> 基于 v3.5.0 → v3.6.0 文档修正过程中暴露的深层架构问题，同步解决钩子合规、注入时机、知识可达性、Session 复用四大技术痛点。
> **状态：已审计，进入决策阶段**

---

## 设计目标（重新排序）

1. **🎯 多 Agent 协作上下文共享**：建立标准化的项目文档体系，让不同 Agent 接手同一项目时零成本理解上下文
2. **项目文档自维护**：建立第四层认知模块，使 Agent 在完成任务后自动评估并更新项目级文档，实现"项目活文档"
3. **钩子合规零违规**：明确每个 skill 的实际触发钩子，消除 `llm_output` / `agent_end` 等纯观察型钩子被误用于 skill 注入的灰色地带
4. **注入时机与职责对齐**：确保 skill 的 `injected_at` 与 Agent 实际能在该时机完成的工作一致
5. **知识可达性保障**：消除"参考文档化后 Agent 无法触达"的策略性知识孤岛
6. **代码与业务规则闭环**：Session 复用等业务规则必须在代码层有对应实现，不能仅靠 Agent 自律

## 问题诊断（4 项核心业务问题）

### 问题 1：regulation skill 实际未注入，存在「幽灵技能」风险

**审计结果**（`src/metacognition/module.js`）：
- `regulation` skill **从未被加载或注入**
- `deviation.js` 和 `attribution.js` 被实例化并传入 Metacognition 构造函数，但代码中**没有任何地方调用**它们的方法
- `regulation/SKILL.md` 存在，但没有任何钩子会读取它
- 用户看到的 `task.deviations` / `task.attributions` 数组始终为空，因为写入接口未连接

**风险**：Agent 被 SKILL.md 告知"偏差发生后要进行归因分析并更新策略"，但插件从未提供过归因分析所需的上下文（deviations/attributions 数据），导致 Agent 只能凭幻觉进行归因。

**决策**：
- ✅ **方案 B**：将 regulation 触发机制明确为 `before_prompt_build`，条件是 `task.deviations.length > 0`
- 在 `_buildExecutionContext` 中，若检测到未处理的 deviations，注入 `regulation/SKILL.md` + 偏差摘要
- 废弃 `injected_at: Deviation 创建后触发` 这种非标准描述

**实施要点**：
```javascript
// 在 _buildExecutionContext 中添加
if (task.deviations?.length > 0 && !task.deviationsProcessed) {
  const regulationSkill = await this.skills.load('regulation');
  // ... 注入 regulation skill + 偏差摘要
}
```

### 问题 2：monitoring 注入时机与职责的时序错配

**审计结果**（`src/metacognition/module.js` `_buildExecutionContext`）：
- monitoring skill 确实在 `before_prompt_build` 注入（task=active 时）
- `llm_output` 是纯观察型，只保存 output 到 task.plan.output，**不返回任何注入**
- Agent 在 `before_prompt_build` 时收到 monitoring，此时**本轮输出尚未生成**

**实际行为**：
- Agent 收到 monitoring skill 后，看到的是「当前阶段目标提醒」，而非「上一轮输出 vs 预期的对比」
- 真正的"偏差检测"实际上是由 Agent 在**收到 monitoring 提醒后，在本轮输出中自行完成**（自我监控）
- 如果 Agent 没有输出 `[STATUS: revising]` 或 `[DEVIATION: xxx]`，插件不知道偏差发生了

**决策**：
- ✅ **重新定义 monitoring 职责**：从"偏差检测器"改为"偏差预防提醒 + 自我监控指引"
- monitoring 在 `before_prompt_build` 注入，职责是：
  1. 展示当前阶段目标，提醒 Agent 对照执行
  2. 若 `task.deviations` 有未处理项，展示历史偏差列表（避免重复犯错）
  3. 提醒 Agent：本轮输出后，若发现偏差，应输出 `[STATUS: revising]` 触发 regulation
- **不拆分** monitoring-prep / monitoring-check，保持单一 skill 降低复杂度
- 若需要真正的"插件端偏差检测"，未来通过 `before_agent_finalize` 实现（解析 Agent 输出中的 `[DEVIATION]` 标记）

**实施要点**：
- 重写 `monitoring/SKILL.md`，frontmatter 改为 `injected_at: before_prompt_build`
- 明确职责边界："提醒 Agent 注意当前阶段目标，以便在后续输出中自我监控"
- 增加「偏差标记规范」：`[DEVIATION: 类型] 描述`

### 问题 3：working-memory 参考文档化后的知识可达性危机

**审计结果**：
- `working-memory/module.js` 只注册了 `before_tool_call` / `after_tool_call` / `subagent_*` / `agent_end` 钩子
- **没有任何 `before_prompt_build` 注入**，working-memory/SKILL.md 标记为 `reference_only`
- Session 复用规则（同 taskFamily 优先复用 idle）写在 planning/SKILL.md 第 5 步，但 planning 只在 draft/pending_approval 阶段注入
- **active 阶段 Agent 看不到任何 Session 管理相关的 skill**

**风险**：
- Agent 在 active 阶段创建子代理时，不知道该复用哪个 sessionId（或是否该复用）
- 长期未活跃 Session 的 idle 标记策略、全局索引异常处理等知识，Agent 在需要时想不起来查阅

**决策**：
- ✅ **方案：轻量级自动注入 + 查阅提醒**
- 在 `working-memory/module.js` 中新增 `before_prompt_build` 钩子
- 注入条件：`task.status === 'active'` 且本轮涉及 `sessions_spawn` / `sessions_send` 等 session 操作
- 注入内容：仅 5 条核心规则（而非完整 173 行文档）

```markdown
【Session 管理速查】
1. 同 taskFamily 优先复用 idle Session
2. 复用时显式指定 sessionId，插件验证状态
3. 子代理完成后，产出摘要回写父 Session
4. 长期未活跃（>30min）Session 自动标记 idle
5. 冲突：并行修改同一文件需主代理协调
```

- 同时在 `monitoring` 的偏差类型列表中增加「Session 管理偏差」：
  - 该复用却新建了 Session
  - 子代理未回传产出摘要
  - 同一文件被并行修改

### 问题 4：Session 复用的业务规则与代码实现存在断层

**审计结果**（`src/working-memory/session.js`）：
```javascript
async createSession(phase, taskFamily) {
  const sessionId = `session:${taskFamily}:${Date.now()}`;  // ← 每次全新
  const existing = await this.state.getSession(sessionId);   // ← 按 sessionId 精确匹配
  if (existing && existing.status === 'idle') {
    // 复用逻辑几乎不可能触发
  }
  // 否则创建全新 Session
}
```

**全局索引**（`working-memory/module.js` `_updateActiveSession`）：
- 维护了 `working_memory:active_sessions` 列表，记录 `sessionId` + `taskFamily` + `status`
- 但**没有暴露给 `session.js` 的复用决策接口**

**决策**：
- ✅ **方案 C**：在 `planning` 阶段由插件主动扫描全局索引，向 Agent 推荐可复用的 Session，Agent 决定接受或新建
- 这是最符合现有架构的方案：保持 Agent 的决策权，插件提供信息支持

**实施要点**：
```javascript
// 新增 Session 推荐接口
async recommendSessions(taskFamily) {
  const activeSessions = await this.state.getSession('working_memory:active_sessions') || [];
  return activeSessions
    .filter(s => s.taskFamily === taskFamily && s.status === 'idle')
    .sort((a, b) => b.lastActive - a.lastActive); // 最近活跃的优先
}

// 在 planning skill 注入时附加推荐列表
const recommendations = await session.recommendSessions(taskFamily);
if (recommendations.length > 0) {
  planningContext += `\n【可复用 Session 推荐】${recommendations.map(...)}`;
}
```

**业务规则更新**：
- 原规则"同一 taskFamily 优先复用 idle Session" → 改为"插件在 planning 阶段推荐 idle Session，Agent 在 Plan 中显式指定复用的 sessionId，插件验证状态"

## 业务逻辑设计：人机协同协商完成

### 6.1 核心模型：用户分配 + 插件督促 + Agent 执行

v4.0.0 采用**人机协同、协商完成**模型：

```
        用户（任务分配者 + 最终确认者）
           /              \
          /                \
   "Agent A，你擅长数据分析，这个任务给你"
          \                /
           \              /
            ↓            ↓
        Agent A（执行） ←→ Agent B（被请求协助）
           ↑                  ↑
           └──── 插件提醒 ────┘
              （做计划、监控进度、和用户沟通）
```

**核心原则**：
- **用户分配任务**：用户根据 Agent 特性，把适合的任务告诉特定 Agent
- **Agent 执行 + 举手**：Agent 执行任务，发现需要其他 Agent 时写入 TODO 请求用户协调
- **插件督促**：在关键节点注入提醒，督促 Agent 做计划、汇报进度、和用户沟通
- **协商完成**：不是强制流水线，而是通过用户协调完成

### 6.2 任务分配与生命周期

**用户分配任务**：

```markdown
用户："Agent A，你擅长数据分析，帮我分析这些上传的PDF"

Agent A 响应：
1. 读取 uploads/（用户上传文件）
2. 在 TODO.md 记录任务：
   ```markdown
   ## 进行中
   - [x] 数据分析 — @agent-A — 18:00开始 — 来源：用户分配
   ```
3. 制定执行计划（被插件督促）
4. 向用户汇报计划："我将按以下步骤分析：1.提取数据 2.清洗 3.可视化 4.结论"
```

**Agent 举手请求协助**：

```markdown
Agent A 执行中发现：
"我擅长数据分析，但发现需要图像识别能力。
建议分配此子任务给擅长视觉的 Agent B。我继续处理数据部分。"

Agent A 在 TODO.md 追加：
## 待分配（用户协调）
- [ ] 子任务：图像识别 — 需要擅长视觉的 Agent — 依赖：Agent A 的数据分析

用户收到后：
"Agent B，你擅长图像识别，帮 Agent A 完成这个子任务"

Agent B 认领：
## 进行中
- [x] 子任务：图像识别 — @agent-B — 18:30开始
```

**任务完成确认**：

```markdown
Agent A 完成数据分析：
→ 自检 [SELF_CHECKED]
→ 向用户汇报成果："数据分析完成，关键发现：..."
→ 将任务移到「待确认」

## 待确认
- [x] 数据分析 — @agent-A — 已完成，请用户确认

用户确认：
→ 用户：[APPROVED]
→ 任务移到「已完成」
→ Agent A 归档版本到 temp/drafts/
```

### 6.3 插件督促机制

插件通过 Hook 注入提醒，在关键节点督促 Agent：

| 时机 | 注入内容 | 目的 |
|------|----------|------|
| `before_prompt_build`（任务启动） | 「请制定执行计划，明确步骤和验收标准，并向用户汇报」 | 督促做计划 |
| `before_prompt_build`（执行中，每 N 轮） | 「请向用户汇报当前进度，确认方向正确」 | 督促沟通 |
| `after_tool_call`（文件变更后） | 「检测到产出，请确认是否需要请求其他 Agent 协助」 | 督促协作判断 |
| `before_agent_finalize`（完成前） | 「任务即将完成，请确认是否已满足用户要求，准备汇报」 | 督促验收 |

**Agent 响应督促**：
- 被督促做计划 → 输出计划并向用户汇报
- 被督促沟通 → 向用户汇报进度
- 被督促协作判断 → 评估是否需要举手
- 被督促验收 → 自检并向用户请求确认

### 6.4 上下文传递机制

**三层上下文**：

```
第 1 层：项目静态上下文（所有 Agent 共享）
├── README.md           → 项目定位
├── metadata.json       → 项目结构
├── CONVENTIONS.md      → 协作规范
└── COLLABORATION.md    → 标记规范

第 2 层：任务动态上下文（Agent 与用户共享）
├── TODO.md             → 当前任务状态
├── .openclaw/events/   → 最近事件（Agent 举手、用户分配等）
└── .openclaw/locks/    → 谁在编辑什么

第 3 层：用户实时意图
├── 用户直接指令        → 任务分配、调整、确认
├── [APPROVED]         → 用户确认通过
├── [REJECTED]         → 用户拒绝，需要修正
├── [USER_BLOCK]       → 用户要求暂停/终止
└── [HELP]             → Agent 请求用户协调
```

### 6.5 典型协作场景

**场景 1：用户直接分配简单任务**
```
用户："Agent A，整理这些PDF"
  → Agent A 制定计划（被插件督促）
  → Agent A 向用户汇报计划
  → Agent A 执行：读取 uploads/ → 输出到 docs/
  → Agent A 自检 [SELF_CHECKED]
  → Agent A 向用户汇报成果："已完成，请确认"
  → 用户：[APPROVED]
```

**场景 2：用户分配复杂任务，Agent 拆解并举手**
```
用户："Agent A，做一份市场分析报告"
  → Agent A 制定计划，向用户汇报："我将分4步：..."
  → Agent A 执行：收集数据（分析 uploads/）
  → Agent A 发现需要竞品视觉分析
  → Agent A 举手："需要图像识别，建议分配给 Agent B"
  → Agent A 在 TODO.md 写入子任务
  → 用户协调：分配子任务给 Agent B
  → Agent B 执行图像识别
  → Agent A 整合数据 + Agent B 的视觉结果
  → Agent A 向用户汇报完整报告
  → 用户：[APPROVED]
```

**场景 3：用户中途调整**
```
用户："Agent A，暂停竞品分析，先做用户调研"
  → Agent A 收到指令
  → Agent A 更新 TODO.md：原任务标记 [USER_BLOCK]，新增用户调研
  → Agent A 向用户汇报调整后的计划
  → Agent A 继续执行用户调研
```

**场景 4：Agent 请求用户澄清**
```
Agent A 执行中发现歧义
  → Agent A："发现 XX 数据缺失，请确认：
     1. 忽略该项
     2. 补充数据后重新分析
     3. 用估算值替代"
  → 用户选择选项 2
  → Agent A 标记 [BLOCKED: 等待用户补充数据]
  → 用户上传数据到 uploads/
  → Agent A 检测 uploads/ 变化，继续执行
```

### 6.6 文档同步规则

**规则 1：Agent 产出后负责同步**
- Agent 完成工作后，判断是否需要更新文档
- 标记 `[DOC_UPDATE: 文档名]` 或 `[DOC_SKIP]`

**规则 2：更新类型映射**

| 变更类型 | 需更新的文档 | 标记 |
|----------|-------------|------|
| 新增目录/模块 | README.md（项目结构） | `[DOC_UPDATE: README]` |
| 新增工具/技能 | skills/ 相关 SKILL.md | `[DOC_UPDATE: SKILL]` |
| 新增知识条目 | knowledge/notes/ 索引 | `[DOC_UPDATE: KNOWLEDGE]` |
| 任务状态变化 | TODO.md | `[DOC_UPDATE: TODO]` |
| 纯局部修改 | — | `[DOC_SKIP]` |

**规则 3：用户是最终确认者**
- Agent 完成更新后，不自行确认
- 将成果移到「待确认」，等待用户 [APPROVED]
- 用户确认后，版本归档到 `temp/drafts/`

### 6.7 冲突检测与协调

**场景：两个 Agent 同时编辑同一文件**

**检测机制**：
- `before_tool_call` 检测到文件写操作时，检查 `.openclaw/locks/`
- 若已锁定，注入提醒

**协调方式**：
```
Agent A 锁定 file.md（执行用户分配的任务）
Agent B 尝试编辑 file.md → 检测到冲突

方案 1：Agent B 等待（监控 .openclaw/locks/）
方案 2：Agent B 通过 .openclaw/events/ 留言给 Agent A
方案 3：Agent B 请求用户裁定优先级
方案 4：拆分文件（各自编辑不同部分）
```

**无冲突的场景**（鼓励并行）：
- Agent A 编辑 `docs/章节1.md`，Agent B 编辑 `docs/章节2.md` → 无需协调
- Agent A 分析 `uploads/数据1.pdf`，Agent B 分析 `uploads/数据2.pdf` → 无需协调

### 6.8 异常处理

| 异常 | 检测 | 处理 |
|------|------|------|
| Agent 长时间无进展 | 用户或插件督促 | Agent 汇报进度或请求 [HELP] |
| 用户长时间无响应 | Agent 标记 [BLOCKED] | Agent 继续其他任务，不阻塞 |
| 文件锁死锁 | 锁过期机制（10分钟） | 自动释放，Agent 重试 |
| 成果不符合预期 | 用户 [REJECTED] | Agent 修正或重新执行 |
| 需求中途变更 | 用户直接表达 | 更新 TODO.md，Agent 调整计划 |
| Agent 发现能力不足 | Agent 举手 [HELP] | 用户分配其他 Agent 协助 |

## 新增模块设计：项目上下文层（Project Context Layer）

### 5.1 设计动机：多 Agent 协作的上下文共享问题

现有三层架构（元认知 / 工作记忆 / 人格发展）管理的是**单个 Agent 的个体认知状态**。但当多个 Agent 操作同一项目时，面临以下问题：

| 场景 | 问题 | 后果 |
|------|------|------|
| 业务 Agent A 刚完成了模块重构 | 归档 Agent B 不知道改了什么 | 项目文档与代码脱节 |
| 新 Agent C 接手项目 | 需要花 10 轮对话才能理解项目结构 | 上下文窗口浪费 |
| 多个 Agent 并行开发 | 各自创建了不同的 TODO 文件 | 进度无法同步 |
| Agent 需要调用项目特定脚本 | 不知道脚本位置、参数、副作用 | 工具调用失败或产生副作用 |

**核心洞察**：人类团队通过 README、架构图、操作手册、任务看板来共享项目上下文。Agent 团队同样需要标准化的「项目上下文层」。

### 5.2 文档体系：四文件契约

项目根目录必须包含以下四个文档，构成 Agent 的「项目上下文协议」：

```
项目根目录/
├── README.md          # 项目总览 —— 人类可读，Agent 快速理解项目定位
├── metadata.json      # 机器可读架构 —— Agent 解析项目结构、依赖、入口
├── SKILL.md           # 操作手册 —— Agent 调用项目工具、脚本的指南
└── TODO.md            # 进度看板 —— 所有 Agent 同步任务状态
```

#### 5.2.1 README.md —— 项目总览

**读者**：人类开发者 + 首次接触项目的 Agent
**内容**：
- 项目定位（一句话描述）
- 技术栈与核心依赖
- 项目结构图（目录树 + 每个目录的职责）
- 快速开始（如何安装、如何运行测试）
- 与其他项目的关系

**Agent 使用方式**：
- 首次接手项目时，先读取 README.md 建立整体认知
- 不需要在每次对话中重复读取，只需在「项目切换」时读取

#### 5.2.2 metadata.json —— 机器可读架构

**读者**：Agent（通过工具快速解析）
**目的**：让 Agent 在不消耗大量 token 的情况下，精确了解项目结构
**内容**：
```json
{
  "project": {
    "name": "agent-self-development",
    "version": "3.5.0",
    "type": "openclaw-plugin",
    "language": "javascript",
    "entry": "src/index.js"
  },
  "architecture": {
    "modules": [
      { "name": "metacognition", "path": "src/metacognition", "hooks": ["before_prompt_build", "llm_output", "before_agent_finalize"] },
      { "name": "working-memory", "path": "src/working-memory", "hooks": ["before_tool_call", "after_tool_call", "subagent_*", "agent_end"] },
      { "name": "personality", "path": "src/personality", "hooks": ["before_prompt_build", "agent_end"] }
    ],
    "dependencies": ["openclaw-extension-api"],
    "tests": "npm test"
  },
  "agents": {
    "supported": ["archiver", "developer", "reviewer"],
    "default": "developer"
  }
}
```

**生成方式**：
- 初始由人类创建
- Agent 在新增/删除模块后，更新 metadata.json 的 `architecture.modules`
- 通过 `[META_UPDATE]` 标记触发更新

#### 5.2.3 SKILL.md —— 操作手册

**读者**：执行业务的 Agent
**内容**：
- **项目特定工具**：如何调用项目的脚本、命令、API
- **代码约定**：命名规范、目录组织、提交格式
- **常用工作流**：测试 → 构建 → 发布的标准流程
- **危险操作清单**：哪些操作需要确认、哪些会产生副作用
- **子模块速查**：每个目录的职责、关键文件入口

**与插件 SKILL.md 的区别**：
| 维度 | 插件 SKILL.md | 项目 SKILL.md |
|------|--------------|---------------|
| 位置 | `src/{module}/SKILL.md` | 项目根目录 `./SKILL.md` |
| 内容 | 插件钩子机制、Agent 行为规范 | 项目工具调用、代码约定、工作流 |
| 更新者 | 插件开发者 | 业务 Agent + 归档 Agent |
| 读者 | 所有使用插件的 Agent | 操作本项目的 Agent |

#### 5.2.4 TODO.md —— 进度看板

**读者**：所有操作本项目的 Agent
**内容**：
- 当前版本的目标和验收标准
- 按 Phase 划分的任务清单（复选框格式）
- 每个任务的负责人（Agent ID）、状态、阻塞项
- 变更日志

**使用协议**：
- Agent 开始任务前，读取 TODO.md 确认当前优先级
- Agent 完成任务后，更新对应复选框状态
- 若发现任务阻塞，添加 `[BLOCKED: 原因]` 标记
- 归档 Agent 定期清理已完成的任务到「历史归档」章节

### 5.3 多 Agent 协作协议

#### 角色分工

| 角色 | Agent ID 示例 | 职责 | 主要操作文档 |
|------|--------------|------|------------|
| **归档/记录 Agent** | `archiver` | 维护 README.md、metadata.json、TODO.md 的完整性 | README.md, metadata.json, TODO.md |
| **业务 Agent** | `developer`, `reviewer` | 执行具体开发/审查任务，遵循 SKILL.md 操作项目 | SKILL.md, TODO.md |
| **监控 Agent** | `monitor` | 检查文档与代码是否同步，触发归档 Agent 更新 | 全部 |

#### 协作流程

```
1. 业务 Agent 完成代码变更
   ├── 执行工具调用（write_file / edit_file / shell）
   └── 在输出末尾标注 [DOC_UPDATE: README|SKILL|TODO|metadata]

2. 监控 Agent 检测到变更（after_tool_call）
   ├── 标记「下轮需要注入 project-context skill」
   └── 若业务 Agent 未标注 [DOC_UPDATE]，自动标记 [DOC_PENDING]

3. 下一轮 before_prompt_build
   ├── 若任务由归档 Agent 执行 → 注入 project-context skill + 变更摘要
   └── 若任务由业务 Agent 执行 → 可选注入轻量提醒

4. 归档 Agent 更新文档
   ├── 读取 TODO.md，确认当前任务状态
   ├── 根据变更类型更新对应文档：
   │   ├── 新增模块 → 更新 README.md（项目结构）+ metadata.json（modules）
   │   ├── 新增工具/脚本 → 更新 SKILL.md（常用工具）
   │   ├── 任务完成 → 更新 TODO.md（复选框）
   │   └── 架构变更 → 更新 metadata.json（architecture）
   └── 输出 [DOC_UPDATED: 文档名] 标记
```

### 5.4 触发时机与注入映射

**核心原则**：项目文档是"活文档"，随代码变更同步生长，**不是任务结束后的回顾性补写**。

| 任务状态 | 注入钩子 | 注入内容 | Agent 职责 |
|----------|---------|---------|-----------|
| `active` | `before_prompt_build`（条件触发） | `project-context skill` 或轻量提醒 | 判断本轮输出/文件变更是否需要同步更新文档，当场执行 |

**注入条件**（满足任一即触发）：
- 本轮 `after_tool_call` 检测到文件写操作
- 本轮 `after_tool_call` 检测到子代理完成且产生了产出物
- Agent 在上轮输出中主动标注了 `[DOC_UPDATE]` 标记
- Agent 在上轮输出中标注了 `[DOC_PENDING]`（监控 Agent 自动触发）

**冷却期机制**：距离上次文档更新至少间隔 2 轮才再次注入，避免 prompt 过长

**与 monitoring 的协作关系**：
```
active 阶段执行循环
    ├── before_prompt_build
    │     ├── 注入 monitoring skill（偏差预防）
    │     └── 若满足条件且已过冷却期，注入 project-context skill（文档维护）
    ├── LLM 生成 → Agent 执行（可能修改文件）
    ├── llm_output（插件缓存输出，纯观察）
    ├── after_tool_call
    │     ├── 记录文件变更
    │     ├── 若业务 Agent 未标注 [DOC_UPDATE] → 标记 [DOC_PENDING]
    │     └── 更新 metadata.json 的变更时间戳
    └── before_agent_finalize（解析 [STATUS: xxx] / [DOC_UPDATE: xxx] / [DOC_SKIP] 标记）
```
    if (changes.length === 0) return;

    const skill = await this.skills.load('project-documentation');
    const snapshot = await this._generateRoundSnapshot(changes);

    return {
      prependSystemContext: `${skill}\n\n【本轮变更快照】${JSON.stringify(snapshot)}`
    };
  }

  async onAfterToolCall(event, ctx) {
    // 检测文件写操作，记录变更
    const isFileWrite = ['write_file', 'edit_file', 'shell'].includes(event.toolName);
    if (!isFileWrite) return;
    // ... 解析变更，加入 _pendingFileChanges
  }

  async onBeforeAgentFinalize(event, ctx) {
    // 解析 [DOC_UPDATE] / [DOC_SKIP] 标记
    const output = event.output || '';
    if (output.includes('[DOC_SKIP]')) {
      this._pendingFileChanges.delete(ctx.runId);
    }
    // ...
  }
}
```

## 项目初始化协议（Project Initialization Protocol）

### 7.1 设计约束

1. **所有文件在项目目录内**：`.openclaw/` 及其子目录放在项目根目录
2. **插件只负责提醒**：通过 `before_prompt_build` / `after_tool_call` 等 Hook 注入 skill 文档，提醒 Agent 该做什么
3. **Agent 具体执行**：Agent 自行决策、读写文件、管理版本、归档草稿
4. **纯文件系统协作**：Agent 之间没有共享上下文，通过文件读写协调

### 7.2 初始化目标

让任意项目在 3 分钟内接入 OpenClaw 协作：

```
普通项目/                          OpenClaw 协作就绪项目/
├── README.md                      ├── README.md
└── ...                            ├── metadata.json
                                   ├── .openclawignore
                                   ├── .mcp.json
                                   ├── .openclaw/
                                   │   ├── README.md
                                   │   ├── events/
                                   │   ├── locks/
                                   │   ├── decisions/
                                   │   └── tasks/
                                   ├── skills/          ← 项目级技能（项目特有）
                                   ├── uploads/          ← 用户上传（只读）
                                   ├── manuscripts/      ← Agent 手稿（进行中）
                                   ├── docs/             ← 定稿文档
                                   ├── knowledge/
                                   │   ├── notes/        ← 结构化笔记
                                   │   └── syntheses/    ← 综合/综述
                                   └── temp/
                                       ├── drafts/       ← 版本归档
                                       └── cache/        ← 缓存
```

### 7.3.1 skills/ — 项目级技能

**定位**：`skills/` 存放**本项目特有的技能**，与 OpenClaw 全局技能（`~/.openclaw/skills/`）区分。

**与全局技能的区别**：

| 维度 | 全局技能（`~/.openclaw/skills/`） | 项目级技能（`项目根/skills/`） |
|------|-----------------------------------|-------------------------------|
| 范围 | 所有项目共享 | 只属于本项目 |
| 内容 | 通用能力（如 `skill-creator`、`project-context`） | 项目特定工具封装、分析逻辑 |
| 示例 | `openclaw-skill-dev/SKILL.md` | `report-analyzer/SKILL.md`（解析本项目日志格式） |
| 更新者 | OpenClaw 生态维护者 | 本项目的 Agent |

**使用场景**：
- 封装「调用本项目的测试脚本」的复杂流程
- 定义「解析本项目日志格式」的分析技能
- 创建「生成本项目报告模板」的自动化技能

**命名规范**：
```
skills/
├── report-analyzer/       # 技能目录
│   ├── SKILL.md           # 技能说明（YAML frontmatter + 使用指南）
│   ├── references/        # 参考文档
│   └── scripts/         # 辅助脚本
└── README.md              # skills/ 目录索引
```

| 目录 | 权限 | 内容 | Agent 职责 |
|------|------|------|-----------|
| `skills/` | 读写 | **项目级技能**（本项目特有的工具封装、分析技能、自动化脚本） | 开发、更新、调用项目特定技能 |
| `uploads/` | **只读** | 用户上传的原始文件 | 读取、分析、提取 |
| `manuscripts/` | 读写 | 进行中的草稿、未审核内容 | 撰写、修改、自我迭代 |
| `docs/` | 读写 | 定稿、已审核、对外发布 | PM/Reviewer 审核后定稿 |
| `knowledge/notes/` | 读写 | 结构化笔记、提取的知识点 | 整理、分类、链接 |
| `knowledge/syntheses/` | 读写 | 综合报告、文献综述 | 基于 notes 综合生成 |
| `temp/drafts/` | 读写 | 历史版本归档 | Agent 判断旧版本时自动归档 |
| `temp/cache/` | 读写 | 中间产物、缓存 | 用完可清理 |

### 7.4 版本控制与归档（Agent 执行）

**插件职责**：在 `after_tool_call` 检测到文件覆盖时，通过 Hook 注入提醒：
> 【提醒】你正在覆盖 `docs/报告.md`。建议先归档旧版本到 `temp/drafts/报告_v1.md`。

**Agent 职责**：
1. 判断是否需要保留旧版本
2. 如需保留，读取旧内容 → 写入 `temp/drafts/报告_v{版本}.md`
3. 版本号规则：从文件名提取 `v\d+`，或自动递增
4. 在 `.openclaw/events/` 记录归档事件

**归档路径模板**：
```
temp/drafts/{title}/{title}_{version}.md
temp/drafts/报告/报告_v1.md
temp/drafts/报告/报告_v2.md
```

### 7.5 文件锁协议（Agent 执行）

**插件职责**：在 `before_tool_call` 检测到文件写操作时，检查 `.openclaw/locks/`，若已锁定则注入提醒：
> 【冲突】`docs/报告.md` 已被 `developer-A` 锁定（2026-05-08 18:00，10分钟后过期）。建议等待或协调。

**Agent 职责**：
1. 写文件前，检查 `.openclaw/locks/{文件路径替换/为-}.json` 是否存在
2. 若不存在，创建锁文件：
   ```json
   {"agent": "developer-A", "lockedAt": "...", "expiresAt": "...", "reason": "..."}
   ```
3. 完成后，删除锁文件
4. 若发现冲突，放弃修改或协调（通过 `.openclaw/events/` 记录冲突）

### 7.6 事件流（Agent 执行）

**插件职责**：在 `after_tool_call` 检测到文件写操作后，**纯观察**记录到内部状态（不写入文件）。下一轮 `before_prompt_build` 若满足条件，注入提醒：
> 【事件】上轮检测到 3 个文件变更。请确认是否需要更新 TODO.md 或归档旧版本。

**Agent 职责**：
1. 将关键事件写入 `.openclaw/events/2026-05-08.md`（追加）
2. 事件格式：
   ```markdown
   - 18:05 developer-A: 完成 `docs/报告.md` 初稿，归档 `temp/drafts/报告_v1.md`
   - 18:10 developer-B: 锁定 `docs/报告.md` 进行审核
   - 18:15 reviewer: [APPROVED] `docs/报告.md`，标记定稿
   ```
3. 定期清理：`.openclawignore` 中配置的保留天数

### 7.7 决策记录（Agent 执行）

**插件职责**：在 `before_agent_finalize` 检测到 `[DECISION: xxx]` 标记时，注入提醒：
> 【归档】检测到决策标记。建议将决策背景写入 `.openclaw/decisions/` 以便追溯。

**Agent 职责**：
1. 关键决策后，写入 `.openclaw/decisions/YYYYMMDD-HHMM-决策简述.md`
2. 内容模板：
   ```markdown
   # 决策：为什么选择方案 B

   ## 时间：2026-05-08 18:00
   ## 决策人：developer-A
   ## 背景：...
   ## 选项对比：A vs B vs C
   ## 结论：选择 B，因为...
   ## 影响范围：...
   ```

### 7.8 初始化触发

| 方式 | 触发者 | 流程 |
|------|--------|------|
| 手动初始化 | 人类或 PM Agent | 执行 `mkdir -p .openclaw/{events,locks,decisions,tasks}` |
| 自动检测 | 任何 Agent | Agent 进入项目发现无 `.openclaw/`，自行创建标准结构 |
| 技能模板 | `skills/project-context/` | 提供 `assets/init-template/` 一键复制 |

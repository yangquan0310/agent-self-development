# v4.0.0 Roadmap: Project Context Layer & Multi-Agent Collaboration

> **核心目标**：建立「项目上下文层」，使多 Agent 能在同一项目中协作。
> **设计哲学**：文档即契约 —— README 是项目总览，metadata.json 是机器可读的架构，SKILL.md 是操作手册，TODO.md 是进度看板。
> **状态**：active
> **创建时间**：2026-05-08
> **预计完成**：2026-05-15

## 1. 问题诊断（Problem Diagnosis）

基于 v3.5.0 → v3.6.0 的代码审计和文档审查，发现以下核心问题：

### 问题 1：regulation skill 实际未注入，存在「幽灵技能」风险

**影响范围**：`src/metacognition/module.js`、元认知架构
**风险等级**：严重
**具体表现**：
- `regulation` skill **从未被加载或注入**
- `deviation.js` 和 `attribution.js` 被实例化但未调用
- 用户看到的 `task.deviations` / `task.attributions` 始终为空
- Agent 被告知要归因分析，但插件从未提供数据

### 问题 2：monitoring 注入时机与职责的时序错配

**影响范围**：`src/metacognition/module.js`、monitoring skill
**风险等级**：严重
**具体表现**：
- monitoring skill 在 `before_prompt_build` 注入，但此时本轮输出尚未生成
- Agent 收到 monitoring 后看到的是「目标提醒」，而非「上一轮输出 vs 预期的对比」
- 真正的偏差检测由 Agent 在收到提醒后自行完成（自我监控）
- 如果 Agent 没有输出 `[STATUS: revising]`，插件不知道偏差发生了

### 问题 3：working-memory 参考文档化后的知识可达性危机

**影响范围**：`src/working-memory/module.js`、Session 管理
**风险等级**：中等
**具体表现**：
- `working-memory/module.js` 只注册了 tool_call / agent_end 钩子
- **没有任何 `before_prompt_build` 注入**，working-memory/SKILL.md 标记为 `reference_only`
- active 阶段 Agent 看不到任何 Session 管理相关的 skill
- Agent 创建子代理时，不知道该复用哪个 sessionId

### 问题 4：Session 复用的业务规则与代码实现存在断层

**影响范围**：`src/working-memory/session.js`、Session 生命周期
**风险等级**：中等
**具体表现**：
- `createSession` 每次生成新的 `Date.now()` sessionId，几乎不可能复用
- 全局索引维护了 `working_memory:active_sessions`，但没有暴露给 `session.js` 的复用决策接口
- 业务规则说"同一 taskFamily 优先复用 idle Session"，但代码无法实现

## 2. 目标凝练（Goal Refinement）

基于上述问题，定义 v4.0.0 的核心目标：

| 目标 | 对应问题 | 成功标准 |
|------|---------|----------|
| **建立项目上下文层** | 问题1-4 | 多 Agent 能在同一项目中协作，零成本理解上下文 |
| **项目文档自维护** | 问题2 | Agent 完成任务后自动评估并更新项目级文档 |
| **钩子合规零违规** | 问题1 | 所有 skill 的触发钩子明确，无灰色地带 |
| **注入时机与职责对齐** | 问题2 | skill 的 `injected_at` 与 Agent 实际能完成的工作一致 |
| **知识可达性保障** | 问题3 | 参考文档化后 Agent 能在适当时机触达 |
| **代码与业务规则闭环** | 问题4 | Session 复用等业务规则在代码层有对应实现 |

## 3. 解决方法与决策（Solutions & Decisions）

### 问题 1 解决方案：修复 regulation 注入机制

**方案**：将 regulation 触发机制明确为 `before_prompt_build`，条件是 `task.deviations.length > 0`
**决策依据**：
- 方案 A（继续不注入）：问题持续存在 → 排除
- 方案 B（`before_prompt_build` 条件注入）：合规且有效 → **选用**
**实施要点**：
1. 在 `_buildExecutionContext` 中检测未处理的 deviations
2. 注入 `regulation/SKILL.md` + 偏差摘要
3. 废弃 `injected_at: Deviation 创建后触发` 非标准描述
**兼容性**：向后兼容，新增注入不影响现有行为

### 问题 2 解决方案：重新定义 monitoring 职责

**方案**：从"偏差检测器"改为"偏差预防提醒 + 自我监控指引"
**决策依据**：
- 方案 A（保持现有）：时序错配持续 → 排除
- 方案 B（拆分为 monitoring-prep + monitoring-check）：增加复杂度 → 排除
- 方案 C（重定义职责为预防提醒））：简单有效 → **选用**
**实施要点**：
1. monitoring 在 `before_prompt_build` 注入，展示当前阶段目标
2. 若 `task.deviations` 有未处理项，展示历史偏差列表
3. 提醒 Agent 本轮输出后，若发现偏差，应输出 `[STATUS: revising]`
**兼容性**：向后兼容，职责定义更新不影响代码

### 问题 3 解决方案：轻量级自动注入 + 查阅提醒

**方案**：在 `working-memory/module.js` 新增 `before_prompt_build` 钩子，session 操作前注入 5 条核心规则
**决策依据**：
- 方案 A（恢复完整自动注入）：prompt 过长 → 排除
- 方案 B（保留参考文档，不注入）：知识不可达 → 排除
- 方案 C（轻量注入 + 查阅提醒））：平衡可达性和 prompt 长度 → **选用**
**实施要点**：
1. 注入条件：`task.status === 'active'` 且涉及 session 操作
2. 注入内容：仅 5 条核心规则（而非完整 173 行文档）
3. 在 monitoring 偏差类型中增加「Session 管理偏差」
**兼容性**：向后兼容，新增轻量注入

### 问题 4 解决方案：Session 推荐接口

**方案**：在 `planning` 阶段由插件主动扫描全局索引，向 Agent 推荐可复用的 Session
**决策依据**：
- 方案 A（修改 `createSession` 自动复用）：改变现有行为 → 排除
- 方案 B（Agent 完全决策）：信息不足 → 排除
- 方案 C（插件推荐，Agent 决定））：保持 Agent 决策权 → **选用**
**实施要点**：
1. 新增 `recommendSessions(taskFamily)` 接口
2. 在 planning skill 注入时附加推荐列表
3. Agent 在 Plan 中显式指定复用的 sessionId，插件验证状态
**兼容性**：向后兼容，新增推荐接口不影响现有逻辑

# v4.0.1 Roadmap: Hook Reliability & Agent Autonomy

> **核心目标**：建立可靠的 Hook 触发机制，统一项目文件命名，剥离插件越界职责——插件只注入提醒+记录日志，Agent 全权执行任务生命周期。
> **状态**：**cancelled（合并至 v4.1.0）**
> **创建时间**：2026-05-10
> **预计完成**：不适用（已合并）
> **决策依据**：update-plan v1.0.0 技能规范 + PM 决策（2026-05-11）：不经历 v4.0.1 独立版本，直接合并至 v4.1.0

## 0. 合并说明

本版本 roadmap 的问题和解决方案已整合进 [v4.1.0 Roadmap](v4.1.0.md)。不再单独执行 v4.0.1 版本。

**合并原因**：

- 单独发布 v4.0.1 会导致 v4.1.0 推翻大量 v4.0.1 工作，造成重复劳动
- **PM 决策**：直接以 v4.1.0 一次性完成"从 Hook 注入到 Tool 暴露"的架构升级

## 1. 问题诊断

### 问题 1：Hook 注册与触发机制不可靠

**影响范围**：`src/metacognition/module.js`、`src/working-memory/module.js`、`src/index.js`
**风险等级**：严重
**具体表现**：
- `before_agent_finalize` 依赖脆弱的正则/字符串检测（如 `[NEED_PLAN]`），Agent 输出稍有格式偏差（空格、换行、流式截断）即检测失败，导致后续 planning skill 不注入，用户感知为「hook 未触发」
- `llm_output`、`agent_end` 属于 fire-and-forget 观察型 hook，2–30 秒超时即丢弃；状态保存（`_saveTask`、`stream.purge`）在超时时被静默跳过，不可靠
- 各模块使用 `.bind(this)` 隐式绑定 handler，无统一错误处理：任一 handler 抛异常即中断后续 hook 链，且错误信息不写入插件日志
- 缺乏可观测性：Gateway 日志不记录 hook 调用详情，插件日志分散在各模块独立文件，无法 grep 排查「某次对话经历了哪些 hook」

**根因**：v4.0.0 直接调用 `api.on()` 注册 handler，未建立基于官方文档的 Hook 抽象层。各模块各自实现错误处理、超时策略和返回值契约，导致行为不一致、失败无感知。

---

### 问题 2：项目文件命名不统一，概念混淆

**影响范围**：所有项目目录、wiki 模板、插件代码中的路径引用
**风险等级**：中等
**具体表现**：
- `.openclaw/` 目录和 `.openclawignore` 文件命名与插件名称 `agent-self-development` 不一致，用户和 Agent 无法直观关联"agent"与".openclaw"
- 三个 wiki 模板页面命名风格各异：`todo-template`（带 `-template`）、`metadata-structure`（带 `-structure`）、`project-directory-structure`（无统一后缀）
- 插件代码中硬编码 `.openclaw` 路径（如 `.openclaw/tasks/{runId}.json`、`.openclaw/events/`），与目录命名脱节

**根因**：v4.0.0 设计初期使用 `.openclaw` 作为工作目录名，后插件定名为 agent-self-development，但目录名、文件名、wiki 页面名未同步更新，形成多套命名体系并存。

---

### 问题 3：插件职责越界，违背「纯钩子框架」设计

**影响范围**：整个插件架构（`metacognition/module.js`、`working-memory/module.js`）
**风险等级**：严重
**具体表现**：
- 插件代码中大量执行文件操作：`_createTask()` 写入 `.openclaw/tasks/{runId}.json`、`_saveTask()` 持久化状态、`_readEventFile()` 读取事件文件
- 插件试图代替 Agent 做决策：检测 `[NEED_PLAN]` 后自动创建 task，而非仅提醒 Agent「需要制定 Plan」
- 插件维护复杂状态机：管理 task.status 转换、phase 推进、偏差记录、事件归档
- 与 v4.0.0 设计宣言「纯钩子框架——只注入提醒，不涉及操作」严重背离，导致架构混乱、调试困难

**根因**：v3.x 遗留代码习惯——插件习惯自己做状态管理和文件操作。v4.0.0 虽然口号改为「纯钩子」，但实现未跟进，插件越界承担了本应由 Agent 执行的职责。

## 2. 解决方法与决策

### 问题 1 解决方案：引入 Hook 抽象层，统一注册/错误/超时/日志

**方案**：新建 `src/common/hook.js` 定义 `Hook` 基类，封装官方文档定义的 hook 类型（modifying / void / claiming）、注册方式、错误捕获、超时策略和统一日志。各业务模块（Metacognition、WorkingMemory、Personality）继承基类注册具体 handler，不再直接调用 `api.on()`。

**决策依据**：
- 方案 A（保留现状，逐模块修复）：需要在 3 个模块中分别统一错误处理、超时和日志，重复工作且容易遗漏 → 排除
- 方案 B（引入 Hook 抽象层）：基类一次性封装官方契约，子类只关注业务逻辑；新增 hook 时自动获得错误捕获和日志 → **选用**

**实施要点**：
1. `src/common/hook.js`：定义 `Hook` 基类，方法包括：
   - `registerModifying(name, handler, options)` — 用于 `before_prompt_build`、`before_agent_finalize`
   - `registerVoid(name, handler, options)` — 用于 `llm_output`、`agent_end`、`model_call_started`
   - `registerClaiming(name, handler, options)` — 预留用于 `before_agent_reply` 等
   - 内部统一：try/catch → 日志 → 不抛异常中断 hook 链；超时按官方默认值；返回值格式校验
2. 各模块移除 `.bind(this)` 和重复的错误处理，改为调用基类方法
3. 基类日志统一输出到 `logs/agent-self-development-hooks.log`，格式：`[timestamp] [hookName] [pluginId] [runId] [status] message`
4. `before_agent_finalize` 的 `[NEED_PLAN]` 检测改为更宽松的匹配（允许前后空格、换行），并增加 `retry` 元数据幂等键

**兼容性**：不修改 `api.on()` 的底层调用，只在插件内部增加封装层；外部行为不变。

---

### 问题 2 解决方案：统一命名为 `.agent` 体系

**方案**：将所有 `.openclaw` 相关命名统一为 `.agent`，三个 wiki 模板统一为 `project-*` 风格，插件代码中所有硬编码路径同步更新。

**决策依据**：
- 方案 A（保留 `.openclaw` 并存）：新旧命名并存，Agent 和插件需要兼容两套路径，复杂度倍增 → 排除
- 方案 B（一次性全局替换）：统一为 `.agent` 和 `.agentignore`，与插件名 `agent-self-development` 对齐，概念一致 → **选用**

**实施要点**：
1. 项目目录：`.openclaw/` → `.agent/`（包含 `events/`、`tasks/`、`locks/`、`decisions/`）
2. 忽略文件：`.openclawignore` → `.agentignore`
3. wiki 模板统一命名：
   - `concepts/project-directory-structure.md` → `concepts/project-directory.md`
   - `concepts/metadata-structure.md` → `concepts/project-metadata.md`
   - `concepts/todo-template.md` → `concepts/project-todo.md`
4. 插件代码中所有 `.openclaw` 硬编码路径替换为 `.agent`
5. `project-directory.md` 中的目录结构说明同步更新

**兼容性**：破坏性变更——现有项目需手动重命名目录；插件升级时需在 CHANGELOG 中标注迁移步骤。

---

### 问题 3 解决方案：插件瘦身，回归纯钩子（只注入 + 日志）

**方案**：删除插件中所有文件操作和状态管理，插件只保留 hook 注册、skill 注入和日志记录。task 生命周期（创建、状态转换、执行、完成）完全交由 Agent 执行。

**决策依据**：
- 方案 A（保留现状，插件代劳）：插件越界做越多，与「纯钩子」设计背离，调试困难，且 Agent 无法自主决策 → 排除
- 方案 B（插件瘦身，Agent 自治）：插件只提醒，Agent 全权执行；职责边界清晰，符合 v4.0.0 设计哲学 → **选用**

**实施要点**：
1. 删除 `src/metacognition/module.js` 中的文件操作方法：
   - 删除 `_createTask()`、`_saveTask()`、`_getTaskFilePaths()`、`_readEventFile()`
   - 删除 `.agent/tasks/{runId}.json` 的读写逻辑
2. 删除 `src/working-memory/module.js` 中的 `archiveTask()` 和所有文件归档逻辑
3. `before_prompt_build` 只注入上下文：
   - 若 TODO.md 有匹配任务，注入「当前 TODO 任务：xxx，请评估是否需要制定 Plan」
   - 不再自动创建 task，不管理 task 状态
4. `before_agent_finalize` 只检测标记并记录日志：
   - 检测到 `[NEED_PLAN]` → 记录日志「Agent 请求创建 Plan」→ 不自动创建 task
   - 检测到 `[STATUS:xxx]` → 记录日志「Agent 报告状态 xxx」→ 不写入状态文件
5. Agent 职责（通过注入的 skill 明确告知）：
   - 读取 TODO 上下文后，自行决定是否制定 Plan
   - 需要制定 Plan 时，自行创建 `.agent/tasks/{runId}.json`
   - 自行推进 task 状态、执行 phase、处理偏差
   - 自行更新 TODO.md 中的任务完成状态

**兼容性**：破坏性架构变更——原依赖插件自动创建 task 的 Agent 需要改为自行创建；但插件行为更纯粹，调试更简单。

## 3. 执行清单

### P0：阻塞项

- [ ] **Hook 抽象层基类**：新建 `src/common/hook.js` 定义 `Hook` 基类
  - 验收标准：基类封装 `api.on()`、统一错误 catch、按官方文档区分 modifying/void/claiming 超时策略、统一日志输出到 `logs/agent-self-development-hooks.log`
- [ ] **Metacognition 模块迁移**：`before_prompt_build` / `llm_output` / `before_agent_finalize` / `agent_end` 改为通过 Hook 基类注册
  - 验收标准：任一 handler 抛异常不中断 hook 链，错误信息写入 hooks 日志；`before_agent_finalize` 不再用隐式 bind
- [ ] **WorkingMemory 模块迁移**：`agent_end` 改为通过 Hook 基类注册
  - 验收标准：fire-and-forget hook 有统一超时和日志记录，超时丢弃时也有日志
- [ ] **Personality 模块迁移**：相关 hook 改为通过 Hook 基类注册
  - 验收标准：所有模块的 hook 注册方式一致，handler 签名和返回值符合官方契约
- [ ] **`[NEED_PLAN]` 检测增强**：`before_agent_finalize` 中正则匹配允许前后空白和换行
  - 验收标准：Agent 输出 `\n[NEED_PLAN]\n` 或 `[ NEED_PLAN ]` 都能被检测到

### P1：重要项

- [ ] **命名全局替换**：所有 `.openclaw` → `.agent`，`.openclawignore` → `.agentignore`
  - 验收标准：grep 全文无 `.openclaw` 残留；新建项目自动生成 `.agent/` 和 `.agentignore`
- [ ] **wiki 模板重命名**：三个模板页面统一为 `project-*` 风格
  - 验收标准：`concepts/project-directory.md`、`concepts/project-metadata.md`、`concepts/project-todo.md` 可正常访问
- [ ] **插件代码路径更新**：删除所有硬编码 `.openclaw` 路径引用
  - 验收标准：`src/` 下无 `.openclaw` 字符串残留
- [ ] **插件删除文件操作**：移除 `_createTask`、`_saveTask`、`_readEventFile`、`archiveTask` 等方法
  - 验收标准：插件代码中无 `fs.readFile/writeFile` 调用（日志模块除外）
- [ ] **插件删除状态机**：不再维护 task.status、phase、deviation 等状态
  - 验收标准：插件不读写 `.agent/tasks/` 目录；状态管理完全由 Agent 负责
- [ ] **注入文本更新**：`before_prompt_build` 注入内容改为「提醒 Agent 自行处理 TODO」
  - 验收标准：注入文本明确告知 Agent「检测到 TODO 任务 X，请自行评估并制定 Plan」
- [ ] **Agent 职责明确化**：更新 SKILL.md，明确 Agent 需自行创建 task、推进状态、更新 TODO.md
  - 验收标准：Agent 读取 skill 后知道「插件只提醒，执行由我负责」

### P2：优化项

- [ ] **TODO 匹配算法增强**：`before_prompt_build` 匹配 TODO 任务时支持语义匹配（非仅关键词），支持优先级排序（P0 优先匹配）
  - 验收标准：模糊描述（如"做那个备份任务"）能匹配到 TODO 中的「Git自动备份」；P0 任务优先于 P2 任务注入
- [ ] **注入上下文精简**：避免重复注入导致 token 浪费，同一 runId 内相同 stage 的 skill 只注入一次
  - 验收标准：同一轮对话中 planning skill 不被重复追加到 system context
- [ ] **钩子调用链可视化**：`logs/agent-self-development-hooks.log` 中记录每次 hook 调用的完整链（哪些 handler 执行了、哪些超时了、哪些抛异常了）
  - 验收标准：单条日志可还原「某次对话经历了哪些 hook、各 hook 执行结果」

## 5. 版本兼容性

- **向后兼容**：无——`.openclaw` 重命名为 `.agent` 是破坏性变更，需手动迁移
- **插件行为变更**：插件不再自动创建 task 或管理状态，原有依赖插件自动化的 Agent 需改为自行执行
- **无数据丢失风险**：仅命名变更和职责剥离，不删除用户数据

## 6. 执行顺序与里程碑

三个问题之间存在依赖关系，必须按顺序推进：

```
里程碑 M1：基础设施（问题1）
  ├─ Hook 抽象层基类
  ├─ 三模块迁移到基类
  └─ 验收：任一 hook 抛异常不中断链，日志可观测

里程碑 M2：架构重构（问题3）
  ├─ 删除插件文件操作（_createTask/_saveTask/archiveTask）
  ├─ 删除状态机（task.status/phase/deviation）
  ├─ 更新注入文本（插件只提醒，Agent 执行）
  └─ 验收：插件代码无 fs 调用（日志除外），Agent 读取 skill 后知道"执行由我负责"

里程碑 M3：命名统一（问题2）
  ├─ .openclaw → .agent 全局替换
  ├─ wiki 模板重命名
  ├─ 插件硬编码路径更新
  └─ 验收：grep 全文无 .openclaw 残留

里程碑 M4：优化项（P2）
  ├─ 匹配算法增强
  ├─ 注入上下文精简
  └─ 钩子调用链可视化
```

**不可并行项**：M2（插件瘦身）依赖 M1（Hook 基类）——必须先有统一的 Hook 注册方式，才能在基类上删除旧文件操作。M3（命名替换）可与 M2 并行，但建议 M2 完成后统一替换，避免在已删除的代码上做无用功。

## 7. 审阅后流程

1. **蓝图确认**：杨权确认或提出修改意见
2. **进入开发**：由其他开发者按里程碑顺序执行代码变更
3. **开发经理（程序员）职责**：
   - 评审每个里程碑的 Pull Request
   - 检查验收标准是否达成
   - 协调 Agent 侧 SKILL.md 更新（需同步到各 Agent 工作空间）
4. **版本发布**：
   - 更新 `package.json` 版本号至 `4.0.1`
   - 编写 `CHANGELOG.md`：包含破坏性变更说明（.openclaw→.agent、插件不再自动创建 task）
   - 编写 `MIGRATION.md`：现有项目手动迁移步骤（重命名目录、更新 Agent 习惯）
   - 推送至 GitHub 并打 tag `v4.0.1`

# v4.3.0 路线图：Object-Driven Tool Plugin

> **类型**：版本路线图  
> **版本**：v4.3.0  
> **日期**：2026-05-19  
> **状态**：🚧 规划中  
> **核心定位**：从「全功能认知框架」退回到「工具插件」——只暴露工具，让 Agent 自主调用完成 task + event 全生命周期管理。

---

## 一、版本目标

### 为什么改变架构？

v4.2.0 及之前的架构是一个「重框架」——包含元认知模块、工作记忆模块、人格模块、Hook 注入、Heartbeat 等。这个架构过于复杂，与 OpenClaw 新插件规范「工具插件」的定位不符。

**v4.3.0 的新定位**：
- **纯工具插件**：只通过 `api.registerTool()` 暴露工具，不做 Hook 注入、不做认知框架
- **对象驱动**：TaskObject + EventObject 是核心，管理 `.agent/tasks/` 和 `.agent/events/` 的全生命周期
- **Agent 自主**：Agent 自行决定何时创建任务、何时记录事件、何时推进阶段、何时归档
- **极简目录**：`src/` 下只保留 `objects/`、`assets/`、`tools/`、`utils/`

## 三、暴露的工具清单

### 3.1 task.* 命名空间（5 个工具）

| 工具名 | 类型 | 描述 | 关键参数 | 返回值核心字段 |
|--------|------|------|----------|---------------|
| `task.create` | 操作 | 创建 draft task | `runId`, `prompt`, `taskType?`, `plan?` | `{ task }` |
| `task.update` | 操作 | 更新 task 状态 | `runId`, `status`, `reason?` | `{ task, previousStatus }` |
| `task.advance` | 操作 | 推进 task 阶段 | `runId`, `phaseId?` | `{ task, previousPhase, nextPhase, isComplete }` |
| `task.query` | 查询 | 查询 task 完整状态 | `runId` | `{ task }` |
| `task.archive` | 操作 | 归档 completed task | `runId` | `{ archived, archivedAt }` |

**TaskObject 内部方法（供 tools 调用，不直接暴露为 Agent 工具）**：

| 方法 | 操作对象 | 说明 |
|------|---------|------|
| `create()` | task.json | 创建任务 |
| `get()` | task.json | 查询任务 |
| `update()` | task.json | 更新状态 |
| `advance()` | task.json | 推进阶段 |
| `archive()` | task.json | 归档任务 |
| `recordDeviation()` | task.json `deviations[]` | **新增**：追加偏差记录 |
| `recordAttribution()` | task.json `attributions[]` | **新增**：追加归因记录，标记偏差为已归因 |
| `setOutcome()` | task.json `outcome` | **新增**：设置任务结果 |
| `linkEventFile()` | task.json `eventFilePath` | **新增**：关联 event.md 路径 |
| `validate()` | task.json | 校验结构 |

### 3.2 event.* 命名空间（2 个工具）

| 工具名 | 类型 | 描述 | 关键参数 | 返回值核心字段 |
|--------|------|------|----------|---------------|
| `event.record` | 操作 | **task 完成后**，从 task.json 凝练生成 event.md | `runId` | `{ eventFilePath }` |
| `event.query` | 查询 | 查询历史事件文件 | `runId?`, `date?`, `type?` | `{ events, count }` |

**EventObject 职责变更**：
- **不再增量追加**：event.md 不是执行过程中逐条追加的日志，而是 **task 完成后一次性生成的总结报告**
- **凝练来源**：从 task.json 的 `plan` / `deviations` / `attributions` / `outcome` 字段中提取，按 assets/event.md 模板渲染
- **写入时机**：由 `event.record` 触发（通常在 `task.archive` 之前或同时调用）
- **文件路径**：`./.agent/events/{date}/{runId}.md`（`date` 取自 task.createdAt 的 YYYY-MM-DD）

**EventObject 内部方法**：

| 方法 | 说明 |
|------|------|
| `generate(runId, task)` | **新增/替换**：读取 task.json，按模板生成完整 event.md |
| `query(filters)` | 扫描 `./.agent/events/{date}/` 目录，解析 Markdown 返回结构化数据 |
| `archive(runId)` | 将 event.md 移动到 archive/ |
| `_renderTemplate(template, vars)` | 模板渲染 |
| `_parseEventFile(content)` | 解析 event.md 返回结构化 JSON |

**总计：7 个命名空间工具**（对比 v4.2.0 的 13 个扁平工具，精简了 guide.* 工具——认知指导由 Agent 自行决策，不再通过工具暴露）

## 四、Agent 全生命周期工作流

```
┌─────────────────────────────────────────────────────────────┐
│                        Agent Layer                           │
│  自行决策：何时 create、何时 record、何时 advance、何时 archive │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                      Tool Plugin Layer                       │
│  task.create  ──→  TaskObject.create()  ──→  .agent/tasks/  │
│  task.update  ──→  TaskObject.update()  ──→  .agent/tasks/  │
│  task.advance ──→  TaskObject.advance() ──→  .agent/tasks/  │
│  task.query   ──→  TaskObject.get()     ──→  .agent/tasks/  │
│  task.archive ──→  TaskObject.archive() ──→  .agent/tasks/  │
│  event.record ──→  EventObject.record() ──→  .agent/events/ │
│  event.query  ──→  EventObject.query()  ──→  .agent/events/ │
└─────────────────────────────────────────────────────────────┘
```

### 4.1 典型工作流

1. **任务启动**：Agent 调用 `task.create` → 创建 `.agent/tasks/{runId}.json`
2. **阶段推进**：Agent 调用 `task.advance` → 更新 task.json 的 `currentPhase`
3. **状态更新**：Agent 调用 `task.update` → 更新 task.json 的 `status`
4. **记录偏差**：Agent 调用 `task.update`（或未来扩展的 task 工具）→ **TaskObject.recordDeviation()** 写入 `.agent/tasks/{runId}.json` 的 `deviations[]`
5. **记录归因**：Agent 调用 `task.update` → **TaskObject.recordAttribution()** 写入 `.agent/tasks/{runId}.json` 的 `attributions[]`，并标记对应偏差为已归因
6. **设置结果**：Agent 调用 `task.update` 或 `task.advance` 完成时 → **TaskObject.setOutcome()** 写入 `outcome`
7. **任务完成 + 生成事件报告**：
   - Agent 调用 `task.archive` → TaskObject 将 task.json 移动到 `.agent/tasks/archive/`
   - **Agent 调用 `event.record`** → EventObject 从已归档的 task.json 中凝练生成 `.agent/events/{date}/{runId}.md`
8. **查询回顾**：Agent 调用 `task.query` / `event.query` → 获取历史状态

**关键原则**：
- **执行过程中**：偏差/归因/结果 只写入 task.json，由 TaskObject 维护
- **任务完成后**：event.md 一次性生成，从 task.json 凝练，不再修改
- **event.md 文件路径**：`./.agent/events/{date}/{runId}.md`（date = task.createdAt 的 YYYY-MM-DD，便于按日期扫描）
- **event.md 文件名**：`{runId}.md`（便于直接查找）

## 六、关键决策

### 决策 1：移除 guide.* 工具

**原因**：v4.2.0 的 `guide.planning` / `guide.monitoring` / `guide.regulation` / `guide.development` 是「插件替 Agent 决策」的残留。在工具插件哲学下，Agent 应该自行决定如何规划、如何监控、如何调节——插件只提供数据（task.query / event.query），不提供指导。

### 决策 2：移除 Hook 注入层

**原因**：工具插件不注入 Hook、不修改 Agent prompt。Agent 通过工具调用主动获取信息，插件被动响应。

### 决策 3：State adapter 降级为 utils/file.js

**原因**：不需要复杂的 adapter 继承体系。直接用 fs promises 读写 JSON/Markdown，TaskObject/EventObject 自己管理业务规则。

### 决策 4：保留 task.json 和 event.md 的契约

**原因**：这是项目上下文层的核心资产。即使插件精简，`.agent/tasks/` 和 `.agent/events/` 的文件格式契约必须保留，确保 Agent 可以跨插件/跨项目理解这些文件。

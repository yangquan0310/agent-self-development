## 一、架构概览

| 维度 | 评估 | 说明 |
|------|------|------|
| **分层清晰度** | ✅ 优秀 | 四层架构（用户/代理/插件/系统底层）边界清晰，权力边界文档完整 |
| **模块职责** | ✅ 良好 | 四大模块（Metacognition/WorkingMemory/Personality/Heartbeat）职责单一 |

| **可移植性** | ❌ 差 | 多处硬编码 `/root/.agents` Linux 绝对路径 |

## 二、架构优势（保持）

### 2.1 HookRegistry 抽象层（v4.1.0 亮点）

`src/common/hook.js` 的设计是本轮架构升级的核心收益：

- 统一封装 `api.on()`，移除模块内的 `.bind(this)`
- 按官方文档严格区分 **MODIFYING / CLAIMING / VOID** 三种 hook 类型
- 统一错误捕获 + 超时保护（5s）+ 专用日志 + 调用链可视化
- **关键设计**：VOID 型 hook 禁止返回任何值，从框架层杜绝了违规注入

### 2.2 Tool-Driven 架构转型

v4.1.0 从"推送式 skill 注入"转为"拉取式 tool 调用"，架构语义更干净：

- 插件层从"决策者"退化为"能力提供者"
- 13 个 tools 按 **查询型（7个）/ 操作型（6个）** 分层，权限边界清晰
- `before_prompt_build` 最小化注入（1-3 句），显著降低上下文噪音

### 2.3 双系统平行运行设计

项目级文件系统（Agent 读写）与系统层持久化（插件归档）分离，符合"Agent 是项目文件系统的唯一写入者；插件只读取项目文件"的原则。

### 2.4 适配器回退设计

State / Memory / Flow / Log 适配器在 `api === null` 时回退到文件系统/SQLite，保留了与 OpenClaw 核心解耦的测试和执行能力。

## 三、架构风险与问题

### 🔴 [RISK-1] 严重：硬编码 Linux 绝对路径（可移植性缺陷）

**问题描述**：以下文件硬编码了 `/root/.agents`，在 Windows/macOS/非 root Linux 环境会直接失效：

| 文件 | 硬编码路径 |
|------|-----------|
| `src/index.js:58` | `const baseDir = '/root/.agents'` |
| `src/common/adapters/state.js:15` | `const DEFAULT_DIR = '/root/.agentssstate/...'` |
| `src/common/adapters/memory.js:8` | `const DEFAULT_DB = '/root/.agentssmemory/...'` |
| `src/common/adapters/flow.js:21` | 默认 dbPath `/root/.agentssflows/...'` |

**影响**：当前项目宣称支持 `node >=18.0.0`，但未声明仅限 Linux root 用户。

**建议**：统一使用 `os.homedir()` 或从 `api` / `config` 获取基础目录，并允许通过环境变量覆盖。

---

### 🟡 [RISK-2] 中等：事件文件路径解析代码重复（DRY 违规）

`_resolveEventFilePath(task)` 的相同逻辑出现在：

1. `src/metacognition/module.js:186`
2. `src/working-memory/module.js:502`
3. `src/personality/module.js:51`
4. `src/tools/metacognition-tools.js:429`

**影响**：事件文件格式变更（如目录结构调整）需要修改 4 处，维护成本高，易遗漏。

**建议**：提取到 `src/common/utils.js` 或新建 `src/common/project-context.js` 作为项目级路径解析器。

---

### 🟡 [RISK-3] 中等：Heartbeat 未接入 HookRegistry（一致性缺口）

`src/common/heartbeat.js:28` 直接使用：

```javascript
this.api.on('heartbeat_prompt_contribution', this.onHeartbeatPromptContribution.bind(this));
```

而其他所有模块均通过 `HookRegistry.register()` 注册。

**影响**：Heartbeat hook 不享受 HookRegistry 提供的错误捕获、超时保护、调用链追踪和返回值校验。一旦 `_aggregateStats()` 抛出异常或超时，可能直接中断 OpenClaw 的 heartbeat 链。

**建议**：将 Heartbeat 注册改为 `this.hookRegistry.register('heartbeat_prompt_contribution', ...)`。

---

### 🟡 [RISK-4] 中等：双重状态更新路径（数据竞争风险）

`Metacognition._parseToolCallResult()`（`module.js:612`）声明自己是"tool handler 的辅助备份（双重保险）"，但：

- Tool handler（`metacognition-tools.js`）已直接读写 `state.saveTask()`
- Hook `before_agent_finalize` 再次解析 `ctx.toolCalls` 并修改同一个 task

**问题**：

1. 两个更新路径无同步契约，存在竞态条件
2. `update_task_status` handler 中 `previousStatus` 的赋值在 `status` 修改之后，返回的是新状态而非旧状态（逻辑错误）
3. `advance_phase` 在 hook 中的备份解析与 tool handler 的实现细节强耦合

**建议**：明确单点写入原则。Tool handler 是状态更新的权威来源，hook 层应只读观察，不二次写入。若需同步，应在 tool handler 返回的结果中携带完整的新 task 快照，由 hook 层做校验而非修改。

---

### 🟡 [RISK-5] 中等：State 适配器内部存储模型不一致

`State` 类同时维护两种持久化模型：

- **Task**：独立文件（`tasks/{runId}.json`）—— 适合高频读写、大对象
- **Session**：集合文件（`sessions.json`）—— 所有 session 挤在一个 JSON 中

**影响**：Session 集合文件在并发写入时存在丢失更新风险（无文件锁），且随着 session 数量增长，读写性能线性下降。

**建议**：Session 也应采用独立文件模型（`sessions/{sessionId}.json`），与 Task 保持一致。

---

### 🟠 [RISK-6] 低：Flow 功能定位模糊（冗余数据层）

文档中 Flow 数据库标记为 **[占位符]**，实际观察：

- `Plan` 类同时使用 `state`（Task JSON）和 `flow`（SQLite）
- Task JSON 已完整维护 `status`、`currentPhase`、`phases[]`
- Flow 数据库维护的 `currentStep`、`stateJson.currentPhase` 与 Task JSON 是**同构数据**

**影响**：两个数据源可能不一致（如 `Plan.completePhase` 更新了 State 但 Flow 更新失败时），且没有自动修复/对齐机制。

**建议**：在 Flow 完成核心职责定义前，评估是否可将 Flow 降为 Task JSON 的只读镜像，或明确 Flow 负责"跨任务依赖/工作流编排"等 Task JSON 不覆盖的领域。

---

### 🟠 [RISK-7] 低：Memory 查询功能已写未通

`Memory.queryHistory()` 已实现（`memory.js:116`），但：

- 文档标记为 **[占位符]**
- 没有对应的 tool 暴露给 Agent（13 个 tools 中无历史查询类 tool）

**影响**：事件数据写入 SQLite 后形成"数据坟墓"——写得多、读得少、Agent 无法主动查询。

**建议**：若短期内不暴露查询 tool，应在文档中明确 ADR；若计划暴露，需设计查询参数和权限控制。

---

### 🟠 [RISK-8] 低：项目级文件路径未集中抽象

`.agentssevents/...`、`.agentsstasks/...`、`.agentsslocks/...` 等路径以字符串字面量形式散落在多个模块中。

**影响**：项目上下文层协议升级（如路径变更）时，修改范围不可控。

**建议**：引入 `ProjectContext` 配置对象或常量模块，集中管理所有项目级路径模板。

---

### 🟠 [RISK-9] 低：Session 全局索引残留

v4.0.0 文档明确"移除 `_updateActiveSession` / `_removeActiveSession`，清理全局索引 `working_memory:active_sessions`"，但：

- `State._set('sessions', ...)` 仍在维护 `sessions.json`
- `CONVENTIONS.md` 中 `working_memory:active_sessions` 仍在 State Keys 表中
- `Heartbeat._aggregateStats()` 仍在调用 `state.listSessions()`

**影响**：文档与实现不一致，新开发者容易误以为 Session 全局索引仍是核心机制。

**建议**：同步更新文档，或彻底移除 Session 全局索引（如果 v4.0.0 设计意图是"文件系统替代 Session 内存复用"）。

## 四、模块耦合度矩阵

| 模块 | Metacognition | WorkingMemory | Personality | Heartbeat | Tools | 评估 |
|------|:-------------:|:-------------:|:-----------:|:---------:|:-----:|------|
| **Metacognition** | — | 间接(state) | 间接(state) | 无 | 双向(toolCalls) | ⚠️ 通过 state 隐式耦合 |
| **WorkingMemory** | 间接(state) | — | 间接(state) | 无 | 间接(state) | ✅ 合理 |
| **Personality** | 间接(state) | 间接(state) | — | 无 | 无 | ✅ 合理 |
| **Heartbeat** | 无 | 无 | 无 | — | 无 | ✅ 合理 |
| **Tools** | 直接(handler+hook解析) | 直接(handler) | 无 | 无 | — | ⚠️ 与 Meta 存在双重写入 |

> 注：所有业务模块通过 `State` 实例共享同一套 JSON 文件，形成"隐式共享内存"耦合。当前无事务机制，并发修改同一 task 时存在覆盖风险。

## 五、数据流健康度

```
Agent 输出 [STATUS]/toolCalls
    ↓
before_agent_finalize (Metacognition)
    ├── [STATUS] 解析 → 直接修改 State.task      ⚠️ 路径1
    └── toolCalls 解析 → 再次修改 State.task      ⚠️ 路径2（与 Tool Handler 重复）
    
Agent 调用 create_plan/update_task_status/...
    ↓
Tool Handler (metacognition-tools.js)
    └── 直接修改 State.task                      ✅ 权威来源
        └── 追加事件文件                          ✅ 项目级写入
```

**核心问题**：State.task 有多个写入者（Tool Handler + Hook Parser），缺乏"单点写入"守卫。

## 七、总结

**当前架构等级：B+**

| 维度 | 评分 | 说明 |
|------|------|------|
| 设计理念 | A | "赋能而非代劳"贯穿始终，Tool-Driven 转型正确 |
| 分层边界 | A- | 四层边界清晰，但存在跨层直接文件访问 |
| 模块内聚 | B+ | 模块职责单一，但存在重复代码 |
| 接口抽象 | A- | HookRegistry 设计优秀，Heartbeat 是例外 |
| 数据一致性 | C+ | 双写入路径 + 双系统同步风险 |
| 可移植性 | D+ | 硬编码 Linux root 路径是明显缺陷 |
| 可维护性 | B | 文档完善，但代码-文档存在不一致 |

**下一步行动建议**：

1. 立即修复 **RISK-1**（硬编码路径）和 **RISK-4**（双重更新），这两类问题会直接影响生产环境稳定性和数据完整性。
2. 将 **RISK-2**（路径解析重复）和 **RISK-3**（Heartbeat 接入 HookRegistry）纳入下一个迭代。
3. 对 **RISK-6**（Flow 定位）召开一次简短的技术方案讨论，决定是补全职责还是降级简化。

# 更新计划撰写技能

> **版本**：v1.0.0
> **用途**：标准化版本更新计划的创建和更新

---

## 快速开始

1. **确定版本号**：遵循语义化版本（MAJOR.MINOR.PATCH）
2. **诊断当前问题**：列出项目当前的核心问题（技术、流程、结构）
3. **设计解决方法**：针对每个问题提出解决方案和决策
4. **制定 TODO**：拆解为可执行的任务项，标注优先级和负责人
5. **写入文件**：保存到 `docs/roadmap/v{x.y.z}.md`

---

## 核心结构（三部分）

### 第一部分：当前问题诊断（Problem Diagnosis）

**目标**：客观描述项目当前的核心问题，不急于提出方案。

**撰写要点**：
- 问题编号 + 标题（一句话描述）
- 问题影响范围（技术/流程/文档/协作）
- 风险等级（严重 / 中等 / 低）
- 具体表现（可验证的事实，不是主观感受）

**示例**：
```markdown
### 问题 1：项目文档与代码不同步

**影响范围**：文档（README、SKILL.md 等）
**风险等级**：严重
**具体表现**：
- README.md 描述的项目结构与 actual 目录不符（缺少 `skills/` 目录说明）
- SKILL.md 中的工具命令已过期（`npm run lint` 不存在）
- 新增模块后未同步更新 metadata.json 的 modules 列表
```

### 第二部分：解决方法与决策（Solutions & Decisions）

**目标**：针对每个问题提出方案，记录决策理由。

**撰写要点**：
- 对应问题编号
- 方案描述（一句话）
- 决策依据（为什么选这个方案，而非其他）
- 实施要点（关键步骤，不展开细节）
- 兼容性评估（向后兼容 / 破坏性变更）

**示例**：
```markdown
### 问题 1 解决方案：建立文档自维护机制

**方案**：通过 `.openclaw/events/` 记录文档变更，Agent 执行后主动标记 `[DOC_UPDATE]`
**决策依据**：
- 方案 A（人工检查）：成本高、易遗漏 → 排除
- 方案 B（插件自动修复）：插件只提醒，Agent 执行 → 符合设计原则 → **选用**
**实施要点**：
1. 定义 `[DOC_UPDATE]` / `[DOC_SKIP]` 标记规范
2. 在 `after_tool_call` 检测文件变更
3. 插件注入提醒，Agent 判断并执行
**兼容性**：向后兼容，新增标记不影响现有流程
```

### 第三部分：执行清单 TODO（Action Items）

**目标**：将解决方案拆解为可验证的任务项。

**撰写要点**：
- 按优先级排序（P0 阻塞 / P1 重要 / P2 可选）
- 每个任务包含：描述、负责人（Agent/用户）、验收标准
- 使用复选框格式 `- [ ]`
- 关联到具体文件或模块

**示例**：
```markdown
## 执行清单

### P0：阻塞项
- [ ] 定义 `[DOC_UPDATE]` 标记规范 — 写入 `docs/COLLABORATION.md`
  - 验收标准：所有 Agent 能正确识别和使用标记
- [ ] 创建 `.openclaw/events/` 目录结构
  - 验收标准：Agent 能成功写入和读取事件

### P1：重要项
- [ ] 重写 `README.md` 项目结构说明
  - 验收标准：与实际目录 100% 匹配
- [ ] 更新 `metadata.json` modules 列表
  - 验收标准：与 src/ 目录一致

### P2：优化项
- [ ] 编写文档同步场景测试
  - 验收标准：覆盖 [DOC_UPDATE] / [DOC_SKIP] / 遗漏检测三种情况
```

## 完整模板

需要完整模板时，读取 [references/template.md](references/template.md)。

模板包含：
- YAML frontmatter 规范（版本、状态、日期）
- 三部分详细框架
- 关联影响表
- 实施策略（Phase 划分）
- 自检清单

---

## 撰写原则

1. **先诊断，后方案**：不跳过问题诊断直接写 TODO
2. **决策留痕**：每个方案说明「为什么选这个」，方便后续追溯
3. **验收可验证**：每个 TODO 项必须有明确的验收标准
4. **兼容性说明**：标注变更是否向后兼容，影响范围
5. **简洁优先**：单个更新计划不超过 500 行，复杂内容拆分到 references

## 文件保存规范

| 版本类型 | 保存路径 | 命名 |
|----------|----------|------|
| 主要版本 | `docs/roadmap/v{major}.0.0.md` | `v4.0.0.md` |
| 次要版本 | `docs/roadmap/v{major}.{minor}.0.md` | `v4.1.0.md` |
| 补丁版本 | `docs/roadmap/v{major}.{minor}.{patch}.md` | `v4.1.1.md` |
| 未发布草稿 | `docs/roadmap/v{x.y.z}-draft.md` | `v4.0.0-draft.md` |

---

## 标记规范

撰写更新计划时使用的标记：
- `[NEED_RESEARCH]` — 需要进一步调研才能决策
- `[DECISION_PENDING]` — 方案未定，等待讨论
- `[BREAKING]` — 破坏性变更，需兼容性处理
- `[COMPATIBLE]` — 向后兼容，低风险
- `[ARCHIVE]` — 完成后归档到 `docs/changelog/`

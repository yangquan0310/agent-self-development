# v3.6.0 更新计划：本地项目文件系统与上下文持久化

> 核心动机：session 作为运行时概念难以重复调用，网关重启或会话超时后上下文丢失。
> 本计划引入本地项目文件系统（Project File System, PFS），用结构化文件替代运行时 session 作为上下文持久化层。
> 基于 v3.5.0 Hooks 合规重构后的架构演进。

---

## 设计目标

1. **上下文持久化**：将项目上下文从运行时内存（`ctx.state`）迁移到本地文件系统，实现跨进程、跨会话的上下文保持
2. **会话可恢复**：新 session 启动时自动加载项目上下文，无需依赖 `ctx.state` 中的运行时状态
3. **人类可审计**：项目上下文以 JSON/Markdown 文件形式存储，开发者可直接查看和编辑
4. **渐进式迁移**：兼容现有 `State` / `Memory` 适配器，不破坏 v3.5.0 已稳定的 Hooks 架构
5. **版本控制友好**：项目上下文文件可纳入 Git 管理，追踪项目演进历史

---

## 问题诊断

### 第一类：Session 运行时依赖（3 项）

| # | 问题 | 当前实现 | 影响 |
|---|------|----------|------|
| 1 | `ctx.state` 是内存存储 | `before_prompt_build` 中将用户 prompt 保存到 `ctx.state.set('prompt:${runId}')` | 网关重启后丢失，新 session 无法读取 |
| 2 | Session 索引依赖运行时 | `sessions.json` 存储在 `~/.openclaw/state/agent-self-development/` | 不同工作目录的 session 混杂，无法按项目隔离 |
| 3 | 子代理 session 追踪脆弱 | `subagent_spawned` 将 `sessionKey` 写入 `task.sessionIds` | task JSON 在 `~/.openclaw/state/` 下，与具体项目分离 |

### 第二类：上下文分散与不可恢复（4 项）

| # | 问题 | 当前实现 | 影响 |
|---|------|----------|------|
| 4 | 任务文件分散 | `state/tasks/{runId}.json` 单文件存储全部任务信息 | 文件过大，plan / phases / deviations 混杂，难以快速定位 |
| 5 | 无项目级索引 | 无 `index.json` 或 `README` 描述当前项目状态 | 新 session 无法判断"这是哪个项目""之前做了什么" |
| 6 | 归档不可检索 | 归档任务在 `state/archive/` 下，无标签/分类 | 历史任务查找困难，人格回顾时无法快速提取相关经验 |
| 7 | 事件日志封闭 | `memory/{agentId}.sqlite` 二进制格式 | 无法直接用文本工具查看，版本控制不友好 |

### 第三类：实际使用痛点（3 项）

| # | 问题 | 场景描述 |
|---|------|----------|
| 8 | 难以"回到之前的任务" | 用户 2 小时前创建了一个复杂任务，新 session 进来后 Agent 不知道之前的进度 |
| 9 | 子代理结果难以追溯 | 子代理完成后，其产出只保存在运行时的 session 中，主代理后续无法直接读取 |
| 10 | 多项目上下文混杂 | 同一 Agent 处理多个项目时，所有任务的 state 文件放在同一目录，无项目隔离 |

## 核心方案：项目文件系统（PFS）

### 文件结构

```
workspace/<agent>/.project/              # 项目上下文根目录
├── index.json                           # 项目索引：活跃任务、最近更新、项目元数据
├── context.md                           # 项目级上下文（人类可读）
├── tasks/                               # 任务存储（替代 state/tasks/）
│   ├── active.json                        # 活跃任务列表（含快捷引用）
│   ├── current.json                       # 当前焦点任务（单任务快捷引用）
│   ├── {runId}/                         # 每个任务独立目录
│   │   ├── task.json                      # 任务基础信息（status, goal, constraints）
│   │   ├── plan.json                      # 计划详情（phases, successCriteria）
│   │   ├── phases/                        # 阶段执行记录
│   │   │   ├── p1.json
│   │   │   └── p2.json
│   │   ├── deviations.json                # 偏差记录（数组）
│   │   ├── attributions.json              # 归因记录（数组）
│   │   ├── tools.json                     # 工具调用记录
│   │   ├── sessions.json                  # 关联会话索引
│   │   └── log.jsonl                      # 任务级日志（JSON Lines）
│   └── archive/                           # 归档任务（按日期子目录）
│       └── 2026-05/
│           └── {runId}.json
├── sessions/                            # 会话持久化（替代 state/sessions.json）
│   └── {sessionKey}.json                  # 每个会话独立文件
├── snapshots/                           # 上下文快照（用于快速恢复）
│   └── {timestamp}.json                   # 项目完整状态快照
└── events/                              # 事件日志（替代 memory sqlite 的部分功能）
    └── 2026-05-08.jsonl                   # 按日期分片的 JSON Lines
```


```
    ▼

    │
    ├── 从 ctx.state 读取 prompt（内存，易失）
    ├── 从 state/tasks/{runId}.json 读取 task（单一文件）

    ▼

    │
    ▼

    │

    ▼

    │
    ├── WorkingMemory：归档 task → state/archive/
```

```
    │

    ├── 从 .project/tasks/{runId}/plan.json 读取 plan

    ▼

    ▼

    ├── 检测 [NEED_PLAN] → 创建 draft task

    ▼

    │
    ├── WorkingMemory：归档 task → .project/tasks/archive/
    ├── Event：打包 task → .project/events/{date}.jsonl（文本，可审计）
    ├── 更新 .project/context.md（人类可读）
    ├── 更新 .project/index.json（项目索引）
```

## 关键设计决策

### 为什么不用 SQLite 而用 JSON 文件？
- **人类可读**：开发者可以直接打开 `.project/tasks/{runId}/plan.json` 查看计划
- **版本控制友好**：Git 可以 diff JSON 文件，无法 diff SQLite 二进制
- **跨工具兼容**：任何文本编辑器、脚本语言都能处理 JSON，无需 SQLite 驱动
- **调试便利**：排查问题时直接 `cat` 文件即可，无需 SQL 查询

### 为什么保留 State 适配器的双写兼容？
- **风险可控**：v3.5.0 刚刚稳定，不应一次性替换存储层
- **回滚能力**：若 PFS 有问题，关闭 `projectMode` 即可回到 v3.5.0 行为
- **平滑迁移**：让各模块逐步迁移到 ProjectContext，而非一次性大改

### 为什么 context.md 是 Markdown 而非 JSON？
- **给人类看**：开发者打开 `.project/context.md` 即可了解项目现状
- **给 Agent 读**：Agent 同样能解析 Markdown，且格式更自然
- **双向编辑**：开发者可以手动编辑 context.md，Agent 读取更新后的内容

### 为什么 prompt 单独存为 prompt.txt？
- **避免 JSON 转义问题**：用户原始输入可能含特殊字符，纯文本更可靠
- **快速查看**：开发者可以直接 `cat` 查看原始需求，无需解析 JSON
- **大文本友好**：Plan 的 prompt 字段可能很长，单独文件避免 task.json 膨胀

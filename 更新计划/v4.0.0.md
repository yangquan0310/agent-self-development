# v4.0.0 更新计划：架构治理与业务逻辑校准

> 基于 v3.5.0 → v3.6.0 文档修正过程中暴露的深层架构问题
> 解决"钩子合规隐患""注入时机与职责错配""知识可达性断层""Session 复用逻辑断裂"四大业务痛点

---

## 设计目标

1. **钩子合规零违规**：明确每个 skill 的实际触发钩子，消除 `llm_output` / `agent_end` 等纯观察型钩子被误用于 skill 注入的灰色地带
2. **注入时机与职责对齐**：确保 skill 的 `injected_at` 与 Agent 实际能在该时机完成的工作一致
3. **知识可达性保障**：消除"参考文档化后 Agent 无法触达"的策略性知识孤岛
4. **代码与业务规则闭环**：Session 复用等业务规则必须在代码层有对应实现，不能仅靠 Agent 自律
5. **项目文档自维护**：建立第四层认知模块，使 Agent 在完成任务后自动评估并更新项目级 README 与 SKILL，实现"项目活文档"

---

## 问题诊断（4 项核心业务问题）

### 问题 1：`regulation` skill 触发机制不明，可能违反钩子合规红线

| 维度 | 现状 | 风险 |
|------|------|------|
| frontmatter | `injected_at: Deviation 创建后触发` | 该字符串不是 AGENTS.md 定义的任一标准钩子名 |
| 合规规范 | AGENTS.md 2.1 节规定 `llm_output` 为**纯观察型**，禁止返回注入 | 如果 regulation 实际通过 `llm_output` 二次注入，则违反红线 |
| 可能路径 A | `llm_output` 检测到 Deviation → 同轮返回 regulation skill | ❌ **违规**：纯观察型钩子返回注入 |
| 可能路径 B | `before_prompt_build` 下一轮注入，条件是 `task.deviations` 有未处理项 | ✅ 合规，但需确认实现是否如此 |
| 可能路径 C | `before_agent_finalize` 返回 `action: 'revise'` → 重建 prompt 时附加 regulation | ⚠️ 合规但时序延迟，Agent 已完成本轮思考 |

**待确认**：
- `src/metacognition/module.js` 中 regulation 的实际触发钩子到底是哪个？
- 如果是 `llm_output`，必须立即重构到 `before_prompt_build`
- 如果是 `before_prompt_build`，frontmatter 应修正为标准钩子名 + `injected_when` 条件

### 问题 2：`monitoring` 注入时机与职责存在时序错配

| 维度 | 现状 | 矛盾 |
|------|------|------|
| frontmatter | `injected_at: before_prompt_build` | LLM 调用**前**注入 |
| 核心职责 | "对照 Plan 检查当前输出，检测预期与实际的偏差" | 需要 LLM 的**输出**作为对比对象 |
| 实际流程 | `before_prompt_build` → 构建 prompt → LLM 生成 → `llm_output`（插件缓存输出）→ 下一轮 `before_prompt_build` | monitoring 在 prompt 构建阶段被注入，但此时本轮输出尚未生成 |

**深层矛盾**：
Agent 在 `before_prompt_build` 时收到 monitoring skill，但本轮还没有输出。它只能：
- （A）检查**上一轮**的输出 → 跨轮检测，延迟一个周期
- （B）基于预期提前预判 → 不是真正的"偏差检测"
- （C）monitoring 的实际检测逻辑分散在 `llm_output`（缓存）+ `before_prompt_build`（提醒）两个阶段

**业务影响**：
如果 Agent 误解了 monitoring 的职责时机，可能在 `before_prompt_build` 阶段就尝试检测偏差，结果因为没有输出而跳过检测，导致偏差漏检。

**待决策**：
- monitoring 是否应拆分为两个协作单元？
  - `monitoring-prep`（`before_prompt_build`）：准备对比基准（Plan 当前阶段目标）
  - `monitoring-check`（`before_agent_finalize` 或 `llm_output` 后的人工触发）：执行实际对比
- 或者，是否应将 monitoring 的职责重新定义为"在每次 prompt 构建时提醒 Agent 注意当前阶段目标，以便在后续输出中自我监控"？

### 问题 3：`working-memory` 参考文档化后的知识可达性危机

| 维度 | v3.5.0 之前 | v3.6.0 修正后 |
|------|------------|--------------|
| 注入方式 | `agent_end` 自动注入 | `injected_at: reference_only`，不再自动注入 |
| Agent 获取方式 | 被动接收（每次运行结束自动看到） | 必须主动记得并查阅 |
| 包含的核心知识 | Session 复用规则、全局索引结构、决策检查点 | 同上，但可达性下降 |
| 迁移措施 | — | 核心复用规则已迁移到 `planning/SKILL.md` 第 5 步 |

**未解决的风险**：

1. **规则碎片化**：`planning` 只覆盖了"制定 Plan 时如何分配 Session"，但 working-memory 中还包含：
   - 运行结束后的任务空间看板检查
   - 长期未活跃 Session 的 idle 标记策略
   - 全局索引异常时的手动整理决策
   这些知识目前没有自动注入的载体。

2. **Agent 记忆依赖**：参考文档化假设 Agent 能记住有这样一个文档并在适当时机查阅。但 Agent 没有长期记忆（除了人格文件），它不太可能在没有提醒的情况下想起查阅 `working-memory/SKILL.md`。

3. **监控盲区**：`monitoring` 的偏差检测范围是否包含"Session 管理偏差"？如果不包含，那 Agent 在 active 阶段分配了错误的 Session（如该复用却新建），没有任何机制会在后续纠正它。

**待决策**：
- 是否应为 working-memory 保留一个**轻量级的自动注入 skill**？
  - 候选钩子：`before_prompt_build`（`task.status === 'active'` 且涉及 subagent/session 操作前）
  - 候选内容：仅保留 3-5 条核心复用规则（而非完整的 173 行文档）
- 或者，将 Session 管理偏差的检测责任明确纳入 `monitoring` 的偏差类型列表？

### 问题 4：Session 复用的业务规则与代码实现存在断层

**业务规则**（来自 `planning/SKILL.md` 和原 `working-memory/SKILL.md`）：
> "同一 `taskFamily` 优先复用状态为 `idle` 的现有 Session"

**代码实现**（`src/working-memory/session.js`）：
```javascript
async createSession(phase, taskFamily) {
  const sessionId = `session:${taskFamily}:${Date.now()}`;  // ← 每次生成新的 timestamp
  // ...
  const existing = await this.state.getSession(sessionId);
  if (existing && existing.status === 'idle') {
    // 复用逻辑只会在 sessionId 精确匹配时触发
  }
  // 否则创建全新 Session
}
```

**断层分析**：

| 层面 | 行为 | 结果 |
|------|------|------|
| Agent 侧（业务规则） | Agent 被告知"同一 taskFamily 优先复用 idle Session" | Agent 在 Plan 中可能不指定具体 sessionId，或期望插件自动复用 |
| 插件侧（代码实现） | `createSession` 按 `sessionId` 精确匹配，而 `sessionId` 包含 `Date.now()` | 几乎不可能精确匹配，除非 Agent 显式指定了之前用过的 sessionId |
| `WorkingMemory` 侧 | `_updateActiveSession` 维护全局活跃索引，记录 `taskFamily` + `status` | 有全局视图，但没有暴露给 `session.js` 的复用决策接口 |

**根本问题**：
复用的**业务意图**（按 taskFamily）和复用的**代码实现**（按 sessionId 精确匹配）不在同一抽象层。

**待决策**：
- 方案 A：修改 `session.js` 的 `createSession`，使其先按 `taskFamily` + `status === 'idle'` 查询全局索引，再决定是否复用
- 方案 B：明确业务规则改为"Agent 必须在 Plan 中显式指定复用的 sessionId，插件只做验证"，将复用责任完全推给 Agent
- 方案 C：在 `planning` 阶段由插件主动扫描全局索引，向 Agent 推荐可复用的 Session，Agent 决定接受或新建

## 新增模块设计：项目文档自维护系统（Project Documentation）

### 5.1 设计动机

现有三层架构中：
- **元认知层**管理"本次任务如何执行"
- **工作记忆层**管理"本次任务使用哪些 Session"
- **人格发展层**管理"我从本次任务中学到了什么（更新 Agent 自身）"

**缺失的维度**："本次任务对**项目本身**产生了什么改变？项目文档是否需要同步更新？"

当前项目中，README.md（730 行）严重膨胀且与代码不同步；不存在项目级 SKILL.md，导致新 Agent 接手项目时需要从零理解上下文。这与 v3.6.0 解决的"文档与代码不同步"问题在**项目层面**同样存在。

### 5.2 模块定位

| 属性 | 说明 |
|------|------|
| 模块名 | `ProjectDocumentation` |
| 位置 | `src/project-documentation/`（与 metacognition / working-memory / personality 并行） |
| 核心文件 | `module.js`, `project-doc.js`, `PROJECT_DOC_SKILL.md` |
| 产出物 | 项目根目录 `README.md`、项目根目录 `SKILL.md` |

**与 personality 的区别**：

| 维度 | Personality（人格发展） | Project Documentation（项目文档） |
|------|------------------------|----------------------------------|
| 更新对象 | Agent 自身（`SOUL.md` / `MEMORY.md` 等） | 当前项目（`README.md` / `SKILL.md`） |
| 存储位置 | `~/.openclaw/workspace/{agent_id}/` | 项目工作目录（`./`） |
| 读者 | Agent 自己 | 人类开发者 + 后续 Agent |
| 内容性质 | 个人风格、信念、If-Then 规则 | 项目架构、工具链、代码约定、操作指南 |

### 5.3 触发时机与注入映射

**核心原则**：项目文档是"活文档"，随代码变更同步生长，**不是任务结束后的回顾性补写**。

| 任务状态 | 注入钩子 | 注入内容 | Agent 职责 |
|----------|---------|---------|-----------|
| `active` | `before_prompt_build`（轻量条件触发） | `project_doc` skill 或轻量提醒 | 判断本轮输出/文件变更是否需要同步更新 README/SKILL，当场执行 |

**注入条件**（满足任一即触发）：
- 本轮 `after_tool_call` 检测到文件写操作（`editor`, `write_file`, `shell` 等工具写入了项目文件）
- 本轮 `after_tool_call` 检测到子代理完成且产生了产出物
- Agent 在上轮输出中主动标注了 `[DOC_UPDATE]` 标记

**与 monitoring 的协作关系**：
```
active 阶段执行循环
    ├── before_prompt_build
    │     ├── 注入 monitoring skill（偏差检测）
    │     └── 若本轮有文件变更，注入 project_doc skill（文档维护）
    ├── LLM 生成 → Agent 执行（可能修改文件）
    ├── llm_output（插件缓存输出）
    ├── after_tool_call（插件检测到文件变更，设置下轮注入标记）
    └── before_agent_finalize（解析 [STATUS: xxx] / [DOC_UPDATE] 标记）
```

**关键区别**：
- `monitoring` 关注"执行是否偏离 Plan"
- `project_doc` 关注"项目文档是否偏离代码现状"

### 5.4 Agent 职责：项目文档更新流程（执行中）

**场景：本轮执行修改了代码，Agent 在下一轮 prompt 构建时收到 project_doc skill**

**步骤 1：回顾本轮变更**

插件提供本轮文件变更快照（而非任务结束后才提供完整摘要）：
```json
{
  "roundId": 3,
  "filesChanged": ["src/xxx.js"],
  "filesAdded": ["src/new-module/module.js"],
  "filesDeleted": [],
  "lastDocUpdateRound": 2,
  "affectedSections": ["新增子模块", "核心数据流"]
}
```

Agent 判断：
- 本轮变更是否影响了 README 中描述的项目结构？
- 本轮变更是否引入了新的工具调用模式，需要更新 SKILL？
- 本轮变更是否改变了代码约定或目录组织？

**步骤 2：增量更新（当场执行）**

| 变更类型 | 即时操作 |
|---------|---------|
| 新增模块/文件 | 更新 README 的项目结构图和目录说明 |
| 新增可复用工具/脚本 | 更新 SKILL.md 的"常用工具"章节 |
| 修改核心接口/数据流 | 更新 SKILL.md 的"子模块说明"和"特殊注意事项" |
| 纯局部实现细节（如单个函数修改） | 跳过，不触发文档更新 |

**步骤 3：标记与追踪**

Agent 在输出末尾可添加标记，影响后续轮次：
- `[DOC_UPDATE: README]` → 已更新 README，插件记录 `lastDocUpdateRound`
- `[DOC_UPDATE: SKILL]` → 已更新 SKILL，插件记录
- `[DOC_SKIP]` → 本轮虽有文件变更，但判定无需更新文档

**与事后回顾的区别**：
- **active 阶段更新**：增量、轻量、随改随记，文档与代码时差控制在**一个轮次**内
- **completed 阶段回顾**：容易产生"做了太多变更，忘了最初改了什么"的信息丢失

**待验证假设**：
- 每轮文件变更都注入 project_doc skill 是否会导致 prompt 过长？
- 是否需要设置"冷却期"（如距离上次文档更新至少间隔 2 轮才再次注入）？

### 5.5 项目级 SKILL.md 的内容规范

项目级 `SKILL.md` 不是插件 skill，而是**项目自身的操作手册**。建议结构：

```markdown
# {项目名} — Agent 操作指南

## 项目概览
- 技术栈、核心依赖、项目结构图

## 代码约定
- 命名规范、目录组织、提交信息格式

## 常用工具与命令
- 测试命令、构建命令、lint 命令

## 子模块/核心文件说明
- 各目录职责、关键类/函数入口

## 特殊注意事项
- 已知坑点、必须遵守的约束、需要人工确认的操作

## 版本历史
- 重大架构变更记录
```

### 5.6 插件职责

```javascript
export class ProjectDocumentation {
  constructor({ api, config, state, skills, logger, log }) {

  register() {
    this.api.on('before_prompt_build', this.onBeforePromptBuild.bind(this));
    this.api.on('after_tool_call', this.onAfterToolCall.bind(this));
    this.api.on('before_agent_finalize', this.onBeforeAgentFinalize.bind(this));
  }

  // before_prompt_build：task=active 且本轮/上轮有文件变更时注入 project_doc skill

  async onAfterToolCall(event, ctx) { ... }

  async onBeforeAgentFinalize(event, ctx) { ... }

  // 辅助：生成本轮文件变更快照（git diff --stat 或文件系统快照对比）
  async _generateRoundSnapshot(projectPath) { ... }
}
```

### 5.7 与 v3.6.0 文档工程的关系

v3.6.0 解决的是**插件自身**的文档系统（`src/docs/`、`AGENTS.md`、skill frontmatter）。v4.0.0 的 Project Documentation 解决的是**项目运行对象**（即 Agent 正在操作的目标项目）的文档自维护。

两者互补：
- v3.6.0：让 Agent 知道"OpenClaw 插件怎么用"
- v4.0.0：让 Agent 知道"当前这个项目是什么、怎么改"

### 5.8 与 personality 的时序对比

| 模块 | 触发时机 | 更新对象 | 更新粒度 |
|------|---------|---------|---------|
| **Project Documentation** | `active` 阶段（**执行中**） | 项目 README/SKILL | **增量、随改随记** |
| **Personality** | `completed` 阶段（**完成后**） | Agent SOUL/MEMORY | **回顾、整体分析** |

**设计意图**：
- 项目文档必须**与代码同步生长**，不能等任务结束才补写（那时 Agent 已遗忘早期变更细节）
- 人格文件适合**任务级回顾**，因为需要完整偏差/归因数据才能做同化/顺应分析

## 实施策略建议

由于 4 个问题相互交织（尤其是问题 3 和问题 4 都涉及 Session 管理，问题 1 和问题 2 都涉及元认知钩子设计），建议按以下顺序调研和决策：

```
Phase 1: 钩子审计（明确现状）
  ├── 读取 src/metacognition/module.js 的所有 gateway.on 注册
  ├── 绘制每个 skill 的实际触发链（哪个钩子 → 什么条件 → 注入哪个 skill）
  └── 输出《v3.5.0 实际钩子注册表》，与 AGENTS.md 2.1/2.2 节对比

Phase 2: 业务规则对齐（决策核心）
  ├── 问题 1：确认 regulation 触发机制，重构或修正文档
  ├── 问题 2：重新定义 monitoring 的职责边界或拆分技能
  └── 问题 4：选择 Session 复用方案（A/B/C），修改 session.js + planning skill

Phase 3: 知识可达性重构（落地）
  ├── 问题 3：根据 Phase 2 的 monitoring 新定义，决定是否加入 Session 管理偏差检测
  ├── 若保留 working-memory 为参考文档，需配套在 monitoring/planning 中增加"查阅提醒"
  └── 若恢复自动注入，需设计轻量版 skill 和明确注入条件

Phase 4: 项目文档层落地
  ├── 创建 `src/project-documentation/module.js` + `project-doc.js`
  ├── 创建 `PROJECT_DOC_SKILL.md`
  ├── 在 `src/index.js` 中注册新模块（依赖注入）
  └── 编写场景测试：task=completed 时是否正确注入 project_doc skill

Phase 5: 一致性验证
  ├── 更新所有 SKILL.md 的 frontmatter、注入上下文、"与其他 Skill 的关系"表
  ├── 更新 AGENTS.md 的钩子映射表（2.2 节）
  ├── 更新 AGENTS.md 新增 project-documentation 模块说明
  └── 运行全量测试 + 新增场景测试（Session 复用、regulation 触发、项目文档更新）
```
